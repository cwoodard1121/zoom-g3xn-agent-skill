# One audio engine makes g3xn gig-ready

Build one daemon-side audio engine first and let everything else hang off it: a single WASAPI shared-mode `sounddevice` stream on the interface at its Windows mix rate, teed into a per-song 24-bit WAV writer with a 5–10 s pre-roll ring, a 16 kHz soxr tap for the existing "Hey Claude" listener, and ring-buffer feeds for analysis. Measured on this PC, that tee costs under 2 % of one core and delivers 100 % of samples, whereas the tempting `auto_convert` shortcut silently dropped 2.6–6 % of audio with no overflow flag ([capture notes, dev-PC soak tests Q1/Q5](notes/windows_audio_capture_recording.md)). On top of it, "band syncing" should become a daemon-owned **band clock** `{bpm, beat, phase, source, confidence}` fed in priority order by Ableton Link, MIDI clock, audio beat tracking and the song's stored tempo, which pushes settled tempos to the pedal with the existing `Pedal.set_tempo` (SysEx target `0x0A`, param `0x02`) while tempo-syncable delay and modulation knobs sit in their note-value positions — the catalog and the pedal's own screen prove those positions exist, so delays follow the band with no new protocol ([pedal notes KQ4](notes/pedal_and_band_tempo_sync.md)). For finding where the band is, the right design is a numpy comb-filter beat tracker constrained to ±10–15 % of the song's BPM (it cannot make the octave error that took the pip-installable `aubio-ledfx` from 148 to 74 BPM after 11 s on a synthetic full mix) plus a two-level online time-warping (OLTW) position tracker aligned to the **band's own rehearsal recording**, with the album kept only as the LRCLIB lyric and cue timeline through one offline MrMsDTW map; the tap/voice clock stays the owner and the trackers are confidence-weighted inputs that take control at ≥0.7 sustained for 3–5 s and release below 0.4 ([beat notes Q6](notes/beat_tempo_tracking.md); [alignment notes Q4/Q7](notes/live_alignment.md)). Of the libraries surveyed, madmom and its ONNX fork failed to install here for want of MSVC Build Tools, BeatNet depends on madmom, and pymatchmaker ships no Windows wheel and says Windows needs Build Tools; the live path should be numpy-only, with Beat This! (MIT) and synctoolbox (MIT) as an optional offline `[sync]` extra and GPL code (aubio-ledfx, aalink) kept out of the MIT suite's hard dependencies. The "actually usable at gigs" wins that no competitor ships are an automated preflight, a measured level-match/soundcheck routine and a set clock with projected end; the design rule that keeps automation safe on stage is arm-and-prompt for any pedal action when the clock is uncertain, with a visible active-source indicator. Everything below is sized for one developer on Windows and Python 3.12, and the device-level numbers must be re-measured on the real interface because the dev PC has only a virtual microphone.

## 1. One WASAPI shared stream feeds disk, whisper and the trackers

The engine's single most consequential choice is the host API and mode. Open exactly one `sounddevice.InputStream` on the interface's WASAPI entry in **shared mode at the interface's Windows mix rate**, `blocksize=0`, `dtype='float32'`, all input channels, default `latency='high'`, `extra_settings=sd.WasapiSettings()` with `auto_convert=False`. Shared mode is the only mode in which the daemon, Chrome's `getUserMedia` scope and a wake-word stream can all read the same interface; exclusive-mode streams "seize the audio endpoint" and preempt shared streams ([Microsoft Learn, Exclusive-Mode Streams](https://learn.microsoft.com/en-us/windows/win32/coreaudio/exclusive-mode-streams)), and on the dev PC an exclusive 48 kHz open made an existing MME stream receive exactly one more callback flagged `input overflow` and then nothing — a silent stall, no exception ([capture notes Q1](notes/windows_audio_capture_recording.md)). Shared mode insists on the mix rate (`Invalid sample rate [-9997]` at 16/48/96 kHz when the endpoint sits at 44.1 kHz) unless `auto_convert=True` inserts Windows' own resampler ([python-sounddevice issue #52](https://github.com/spatialaudio/python-sounddevice/issues/52); [sounddevice platform settings](https://python-sounddevice.readthedocs.io/en/0.5.6/api/platform-specific-settings.html)), and that resampler is the trap: in 30 s soak tests WASAPI shared at the native rate, WASAPI exclusive and WDM-KS each delivered **100.0 %** of samples, while **WASAPI shared with `auto_convert=True` delivered 97.4 %, and 84.5 s of audio in 90.0 s (93.9 %)** in the 90-second engine prototype, in every case with no `input_overflow` flag ([capture notes Q5](notes/windows_audio_capture_recording.md)). So set the interface's Default Format to 48 kHz/24-bit once in Windows Sound settings, read `sd.query_devices(dev)['default_samplerate']` at start, open at exactly that rate, and resample inside the daemon for anything that wants another rate. Leave `SD_ENABLE_ASIO` unset: the 0.5.6 wheel bundles an ASIO DLL that is loaded only when that variable is set before import ([sounddevice installation](https://python-sounddevice.readthedocs.io/en/0.5.6/installation.html)), and ASIO buys nothing for recording-plus-analysis while costing shared-mode coexistence. The dev PC's defaults show why the current `voice.py` code is on the wrong API: `sd.default.hostapi` is MME, so the `device=None` that `LaptopMic` and `WakeListener` pass opens the MME entry, which truncates names to 31 characters and reports every timestamp as 0.0; only the WASAPI entries carry absolute times on the `Stream.time` clock ([capture notes Q1](notes/windows_audio_capture_recording.md)). `voice.microphones()` should list WASAPI entries, and the persisted device should be a space-separated query such as `"Scarlett 2i2 WASAPI"` resolved with `sd.query_devices(q, kind='input')` (a comma breaks the substring match) ([capture notes Q5](notes/windows_audio_capture_recording.md)).

The callback does two things only — copy the block into a `queue.SimpleQueue` tagged with `time_info.currentTime` and the running frame count, and write it into a native-rate numpy ring — because PortAudio forbids allocation, file access and blocking calls inside it and stops calling a callback that raises ([sounddevice streams docs](https://python-sounddevice.readthedocs.io/en/0.5.6/api/streams.html)). A writer thread owns everything downstream: the WAV file, a `soxr.ResampleStream` producing the 16 kHz mono feed, per-block meters, and the clock model. Threads, not asyncio, on the audio side: soundfile, soxr and PyAV release the GIL in C, and the FastAPI loop only needs periodic stats pushed through the existing WebSocket hub via `loop.call_soon_threadsafe`. Measured costs make the budget concrete: WASAPI shared callbacks arrive in **480-frame (10 ms) blocks at 48 kHz** with `cpu_load` 0.005–0.010; soxr `ResampleStream` from 48 kHz stereo to 16 kHz mono costs **0.19–0.41 % of a core** across quality settings (HQ 0.36 %); writing 24-bit WAV costs 0.33 %; the 90 s prototype (capture → queue → WAV writer + soxr + 10 s ring, with a second MME stream open beside it) finished with 8,450 callbacks, zero overflows and a queue depth never above 2 ([capture notes Q2](notes/windows_audio_capture_recording.md)). The whole tee is roughly 1–2 % of a core; the one unmeasured interaction is GIL contention from faster-whisper's CTranslate2 bursts, so the engine should log overflow counts and `cpu_load` during a real "Hey Claude" transcription before the first gig.

The wake-word listener shares the engine by subscription rather than by opening a second stream. `WakeListener.feed()` already expects 30 ms frames at 16 kHz and `LaptopMic.stop()` returns 16 kHz mono, so when the voice mic is a channel on the interface, both become consumers of the engine's soxr tap re-framed into 480-sample blocks ([capture notes Q2](notes/windows_audio_capture_recording.md); [g3xn/voice.py](../../g3xn/voice.py)). When the voice mic is a different physical device — the memory notes say a wireless mic goes into the laptop at gigs — keep a second stream on that device; two devices never conflict. The rule that matters is that the engine owns every `sounddevice` stream in the process, because the only way to re-enumerate devices after a mid-show USB reconnect is `sd._terminate(); sd._initialize()`, which closes every open stream ([PortAudio docs](https://www.portaudio.com/docs/v19-doxydocs/portaudio_8h.html); [capture notes Q5](notes/windows_audio_capture_recording.md)). Hot-plug detection can come from pycaw's `MMNotificationClient` (Core Audio `IMMNotificationClient`, Python 3.10–3.14) ([pycaw callbacks.py](https://raw.githubusercontent.com/AndreMiras/pycaw/master/pycaw/callbacks.py); [pycaw README](https://github.com/AndreMiras/pycaw)), with the caveat that its COM threading beside uvicorn and pywebview is untested; a watchdog that alarms when no callback arrives for 2 s or when delivered frames ÷ rate diverges from `stream.time` by more than 0.5 % is the fallback and catches the silent WASAPI loss above. Never stop the stream between songs or in the break: audio vendors' Windows checklists exist precisely because interfaces "disconnect or stop working after a period of inactivity" under USB selective suspend, and the fix is to disable it globally and on the interface's root hub and host controller, plug in directly, and use the high-performance power plan ([Rational Acoustics KB](https://support.rationalacoustics.com/support/solutions/articles/150000091757--windows-audio-device-disconnects-or-stops-working-after-inactivity-within-smaart); [MOTU troubleshooting](https://motu.com/techsupport/technotes/troubleshooting-windows-audio)).

Record live to **plain WAV PCM_24 at the mix rate with python-soundfile** (0.14.0, pure-Python wheels for win_amd64, libsndfile 1.2.2) ([soundfile on PyPI](https://pypi.org/project/soundfile/)). The format choice is a crash-safety result, not a taste: in a test that killed the writer with `os._exit(1)` five seconds in, the **WAV read back all 240,000 frames** in both libsndfile and ffmpeg (both treat a data-size field of 0 as "to end of file"), the **RF64 read as 0 frames**, and the **FLAC was unreadable by libsndfile** (ffmpeg recovered all but the last 2,432 samples) ([capture notes Q3](notes/windows_audio_capture_recording.md)). The cost is **1.04 GB per hour** for stereo 48 kHz 24-bit (691 MB/h at 16-bit, 1.38 GB/h float32), which a 4 GB WAV holds 4.1 h of — enough for a show but irrelevant, because the per-song splitter keeps every file small and the show is the ordered list of segments in a `show.json` manifest, never one giant file. On daemon start, scan for WAVs whose RIFF/data size fields are still 8/0 and patch them so ordinary players accept them. After a song's file closes, a worker transcodes with the **PyAV 19.0.2 that faster-whisper already installs** (there is no ffmpeg CLI on the machine): FLAC for the archive (~0.4 % of a core; 50–70 % of WAV on real music), and AAC-m4a with `movflags=faststart` (160 kb/s, ~75 MB/h, 3.5 % of a core, `moov` atom first so `<audio>` gets duration and Range seeking immediately) or MP3 with an Xing header for the ghost band and the phone ([capture notes Q3](notes/windows_audio_capture_recording.md)). Promotion to the ghost band should write the m4a straight into `~/.g3xn/tracks/<song-key>/track.m4a` with its `info.json`, not pass through `PUT /api/tracks/{key}` whose upload `LIMIT` is 80 MB ([g3xn/tracks.py](../../g3xn/tracks.py)); a five-minute song at 160 kb/s is about 6 MB, so even the limit would not bite, but the direct path avoids a pointless re-upload. Live Opus/AAC encoding during the show is not worth its 3–4 %; do it after close.

Per-song splitting with pre-roll is where the ring buffer earns its place twice. Field recorders do exactly this with a DSP buffer: the Zoom H6's Pre Rec "start[s] recording two seconds before pressing the button" ([Zoom H6 manual p.27](https://www.manualslib.com/manual/2621329/Zoom-H6.html?page=27)); g3xn can afford 5–10 s because the ring is also the analysis look-back and a 10 s stereo ring is ~3.8 MB updated at no measurable cost ([capture notes Q4](notes/windows_audio_capture_recording.md)). The split trigger must be the stage's **song-change event**, debounced by about 2 s, not raw patch changes, because a song can span several patches; the daemon already learns the current song from `POST /api/stage/state`, which the stage view sends every couple of seconds, and from the `stage` events it relays ([g3xn/daemon.py](../../g3xn/daemon.py)). On change, open `~/.g3xn/recordings/<YYYY-MM-DD>_<gig-slug>/<NN>_<song-key>_<HHMMSS>.wav`, write the last N seconds of the ring first, keep the previous file open for a 3–5 s post-roll, and write a sidecar JSON with the song key, gig, wall start, the first sample's index and `perf_counter` time, pre-roll seconds, device, rate, channels and overflow count. Between-song chatter becomes its own "gap" segment so the full show is lossless. Browser recording is ruled out for the band mix: Chrome throttles a hidden page's timers to once a minute after five minutes ([Chrome blog, timer throttling](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)), and Chrome's MediaRecorder WebM carries no Cues (and, chunked, no Duration) so it cannot seek without a server-side remux ([addpipe, 2026-05-29](https://blog.addpipe.com/duration-in-webm-videos-produced-by-chrome/)). The phone stays the second voice source it already is.

Metering belongs in the writer thread and turns the recap's "3 dB off" from a browser estimate into a daemon measurement: per 10 ms block, RMS and peak in dBFS per channel with a 1–2 s peak hold for the scope (so the phone can subscribe to a `level` WebSocket event instead of capturing on its own), a 3 s short-term LUFS for a live "level versus set" indicator, and at song close integrated LUFS and loudness range over the closed WAV with pyloudnorm 0.2.0 (ITU-R BS.1770-4, released 2026-01-04) ([pyloudnorm on PyPI](https://pypi.org/project/pyloudnorm/)). LUFS is the unit that matches what "feels" 3 dB louder; peak dBFS only tells whether the interface clipped ([EBU R 128](https://en.wikipedia.org/wiki/EBU_R_128)). Loopback capture of what the laptop plays is unnecessary — the daemon knows the ghost band's playback position — and in any case the 0.5.6 wheel's PortAudio (`V19.7.0-devel`) exposes no `[Loopback]` devices because PortAudio has not released since 19.7.0 despite merging loopback in 2022 ([PortAudio PR #672](https://github.com/PortAudio/portaudio/pull/672); [python-sounddevice issue #510](https://github.com/spatialaudio/python-sounddevice/issues/510)); PyAudioWPatch 0.2.12.9 is the maintained alternative if it is ever wanted ([PyAudioWPatch on PyPI](https://pypi.org/project/PyAudioWPatch/)).

The clock model is what lets a beat or a position found in the ring land on the stage's timeline. On Windows, PortAudio's stream clock is `time.perf_counter()` — the difference measured as 0.0000 s — while `time.monotonic()` on Python 3.12 is `GetTickCount64()` with 15.6 ms granularity (3.13 moves it to QPC) ([capture notes Q8](notes/windows_audio_capture_recording.md); [What's New in Python 3.13](https://docs.python.org/3/whatsnew/3.13.html)). So the wall time of a block's first sample is `time_info.currentTime − stream.latency` (22 ms shared, 20 ms exclusive on the dev PC), and sample arithmetic gives every later sample; keep a slow linear fit of (cumulative frames → `currentTime`) because interface clocks drift ±10–100 ppm, up to 360 ms per hour ([ASIO4ALL, device aggregation](https://asio4all.org/device-aggregation/)). Do not use `inputBufferAdcTime` on this build: it arrived 20–30 ms *after* `currentTime`, the opposite of its documented meaning ([capture notes Q8](notes/windows_audio_capture_recording.md); [sounddevice streams docs](https://python-sounddevice.readthedocs.io/en/0.5.6/api/streams.html)). Analysis consumers should receive absolute sample indices, not times, and a one-time click calibration (play a click from the daemon, detect it in the capture) measures the residual interface-plus-USB offset that `stream.latency` does not report. In `pyproject.toml` this is a new `record` extra — `sounddevice>=0.5.6`, `soundfile>=0.14`, `soxr>=1.1`, `numpy`, `pyloudnorm>=0.2`, optionally `pycaw` — alongside the existing `voice` extra; PyAV comes with faster-whisper ([pyproject.toml](../../pyproject.toml)). The API it should expose for the user to design screens against: `GET /api/audio` (WASAPI devices with channels, mix rate, the chosen device, stream state, latency, watchdog counters), `PUT /api/audio/device`, WebSocket `level` events at ~10 Hz, `GET /api/recordings` and `GET /api/recordings/{gig}/{segment}` (manifest, sidecar JSON, LUFS, a Range-served audio URL), and `POST /api/recordings/{segment}/promote` into the ghost band.

## 2. A ±15 % prior and the band's own rehearsal take are worth more than any neural tracker

### The tempo and beat tracker: hand-rolled numpy comb filter with the gig's BPM as a prior

Four codebases actually track beats causally, and the install picture on Windows with Python 3.12/3.13 decides most of the choice. The maintained fork `aubio-ledfx` 0.4.12 (uploaded 2026-10-03, `Requires-Python >=3.11`) ships `cp311`–`cp315` win_amd64 wheels and installed cleanly on both 3.12 and 3.13 here (4.96 s on 3.12); madmom from git main and `madmom-onnx` both died with "Microsoft Visual C++ 14.0 or greater is required" on both versions, and madmom's 2018 PyPI release is broken on NumPy ≥1.24 with no maintained release in sight ([aubio-ledfx PyPI](https://pypi.org/pypi/aubio-ledfx/json); [beat notes Q1, install log](notes/beat_tempo_tracking.md); [madmom issue #527](https://github.com/CPJKU/madmom/issues/527); [madmom issue #550](https://github.com/CPJKU/madmom/issues/550)). BeatNet inherits every madmom problem, adds PyTorch, and its stream mode opens its own PyAudio device instead of accepting chunks ([BeatNet.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/BeatNet.py)); BTrack's PyPI package ships macOS-arm64 wheels only ([btrack-beat-tracker PyPI](https://pypi.org/pypi/btrack-beat-tracker/json)); essentia has no Windows wheel at all ([essentia on PyPI](https://pypi.org/project/essentia/)). Accuracy does not rescue the heavy options: on GTZAN, online beat F1 runs **74–81 %** (BeatNet 75.4, BEAST 80.0, BeatNet+ 80.6) against 79–89 % offline, but online **downbeat F1 is only 46–57 %** (Rock Corpus: 73.1 beat / 45.0 downbeat) — a coin flip per bar — so no audio-only tracker can be allowed to own the bar phase ([BeatNet paper](https://ar5iv.labs.arxiv.org/html/2108.03576); [BeatNet+ paper](https://transactions.ismir.net/articles/10.5334/tismir.198); [BEAST](https://arxiv.org/abs/2312.17156)).

The first-hand benchmark shows what the cheap tracker does and why it needs a prior. On a synthetic 148-BPM "band" (kick on 1 and 3, snare on 2 and 4, eighth-note hats, strums on every beat), aubio-ledfx reported the tempo within 2 % at **1.49 s**, emitted its first beat at 1.62 s, matched beats with **|error| 1.8 ms mean, 4.1 ms p95**, and used **0.16 % of one core** — then at ~11 s it **halved to 74 BPM and stayed there**, emitting only every other beat (39/60 matched). The drumless strum-only version held 147.6 BPM for the whole 24 s (56/60, 3.4 ms mean error), and under a 5 % accelerando the tracker followed with beats ~10 ms late ([beat notes Q6](notes/beat_tempo_tracking.md)). The octave error is structural: aubio's Rayleigh prior is hard-wired to prefer 120 BPM (`rayparam = 60*samplerate/120/hop_size`), it has no min/max BPM API, and the kick–snare two-beat cycle competes with the beat period ([aubio beattracking.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/beattracking.c)). A tracker that evaluates the comb or autocorrelation **only at lags within ±10–15 % of 60/BPM_song cannot make that error**, and a tempo-range restriction is also the lever the literature identifies: the DBN's default 55 BPM floor alone forced wrong double-tempo inference on 21 % of SMC tracks ([SMC Blind Spot](https://arxiv.org/abs/2605.12287)). That is why the recommendation is a ~150-line numpy implementation rather than aubio as-is, and the fact that aubio-ledfx and BTrack are GPLv3 while the suite is MIT ([LICENSE](../../LICENSE)) settles it for distribution.

The recipe, with the gig's stored BPM as prior: mono float32 at the interface rate, hop 512, frame 1024 Hann, log-magnitude spectrum, half-wave-rectified spectral flux kept in three bands (kick <150 Hz, snare 150 Hz–2 kHz, hats >2 kHz); an 8 s ODF ring; every 0.5 s an ACF or 3-tooth comb only over lags in `[60/(1.15·BPM), 60/(0.85·BPM)]` with parabolic peak interpolation, requiring the peak/mean ratio to clear a threshold on two consecutive evaluations (lock in ≈2 bars); phase by projecting the last 8 beats of ODF onto candidate phases and correcting per beat with an alpha gain of 0.3–0.5 so a fill does not yank the clock; beats *predicted* ahead, so the reporting latency is effectively zero once locked; and a confidence `min(comb peak/mean ratio, fraction of the last 8 predicted beats with an ODF peak within ±40 ms, 1 − |IBI jitter|/P)` published with every emission ([beat notes Q6/Q8](notes/beat_tempo_tracking.md)). A kick-on-1/snare-on-2-and-4 bar matcher restricted to the four candidate phases of a locked period is cheap and, for this repertoire, likely better evidence than a general-purpose network — but it only ever *confirms or flags* the tap's bar phase, never overrides it silently. The part map should switch the expected period for half-time or double-time sections. State is the app's, not the tracker's: LOCKED (≥6 consecutive beats within ±40 ms of prediction), COASTING (no onsets for ≤2 bars, predictions continue), UNLOCKED (>2 bars of silence or inconsistent intervals → reset, require the tap). The click branch and the no-click branch differ only in parameters: with a click, store the click BPM per song (it can differ from the album BPM the clock ratio uses), narrow the range to ±3 %, and let the tracker's job be drift-correcting the tap over minutes; without one, keep ±10–15 %, a 4–8 s window and per-beat phase correction. Count-ins are a convention, not a detection: four stick clicks at 148 BPM last 1.6 s, exactly one analysis step ([beat notes Q5](notes/beat_tempo_tracking.md)). Prefer the full mix or a room/overhead channel to the guitar DI: BeatNet+ calls non-percussive material "challenging" and gains 8–13 F1 points only with a specially adapted model ([BeatNet+ paper](https://transactions.ismir.net/articles/10.5334/tismir.198)), while a rhythm-guitar DI is a clean onset source for strummed parts and useless during sustained chords and solos. Offline, the right tool is **Beat This!** (`pip install beat-this` 1.1.0, MIT code and weights, torch ≥2) to annotate each stored reference recording with beats and downbeats once, producing the bar grid the live tracker is aligned to ([beat_this GitHub](https://github.com/CPJKU/beat_this); [beat-this PyPI](https://pypi.org/pypi/beat-this/json)).

### The position tracker: two-level OLTW against the rehearsal, album only as the lyric timeline

Online time warping is the only alignment family with twenty years of live-concert use and maintained Python code; HMM followers were "sticky" and three to four times worse in the one side-by-side Python benchmark (OLTW-Arzt MAE 91 ms versus HMM 346 ms on piano) ([Park et al., ISMIR 2025](https://arxiv.org/html/2510.10087v1)). Every production tracker converged on the same features — chroma for harmony plus an onset-emphasising spectral-difference stream, 46 ms windows, 20–23 ms hops, a 5–10 s search band — and a second coarse stream (600 ms frames, 300 ms hop) for acquisition and lost-detection ([Arzt & Widmer, STAIRS 2010](https://www.cp.jku.at/research/papers/Arzt_Widmer_STAIRS_2010.pdf); [Dixon 2005](https://webspace.eecs.qmul.ac.uk/s.e.dixon/pub/2005/ijcai05.pdf)). Per-frame costs are tiny: chroma 3.05 ms and the onset-sensitive LSE feature 0.91 ms, OLTW-Arzt's step 0.07 ms in Cython and 1.22 ms in Python; CQT costs 14× chroma for worse accuracy and MFCC is the worst online and tuning-sensitive on guitar, so drop both ([Park et al.](https://arxiv.org/html/2510.10087v1); [Grachten et al., ISMIR 2013](https://archives.ismir.net/ismir2013/paper/000158.pdf)). The one maintained library, `pymatchmaker` 0.4.0 (Apache-2.0, 2026-10-27), is a reference implementation rather than a dependency: no Windows wheel and no Windows CI, a score-based API that synthesises its reference with FluidSynth, a PyAudio device layer that would duplicate the engine, and no confidence output ([pymatchmaker on PyPI](https://pypi.org/project/pymatchmaker/); [unittest.yml](https://raw.githubusercontent.com/pymatchmaker/matchmaker/develop/.github/workflows/unittest.yml)). Its `oltw_arzt.py` logic is worth reading and re-implementing in ~50 numpy lines; a 500-cell band update is well under 1 ms.

The reference should be the band's own rehearsal recording captured from the same interface, and the evidence is direct. Replacing a synthesised reference with one real performance lifted online accuracy on the hardest orchestral material from **71 % to 80 %** within 250 ms (Mahler) despite the extra offline-alignment error, the authors noted that recordings sharing one piano and setup "will have a positive influence", and the live Concertgebouw deployment with a single annotated performance as the score reached 78 % of downbeats within 250 ms and 92 % within 500 ms with "no glitches" ([Arzt & Widmer, ISMIR 2015](https://www.cp.jku.at/research/papers/Arzt_Widmer_ISMIR_2015.pdf)). For a cover band the gain should be larger, because the rehearsal removes the two documented killers at once: structural mismatch (a plain band-limited OLTW "gets lost at the first score jump" and never recovers ([Brazier & Widmer 2021](https://arxiv.org/pdf/2105.08531v1)); MATCH's guitar alignments failed "due to many differences in the arrangements" ([MATCH 2005](https://archives.ismir.net/ismir2005/paper/000002.pdf))) and feature mismatch (same players, room, gear, tuning — a half-step-down band against a standard-tuned album is a chroma shift the tracker would otherwise have to estimate). The album keeps one job: it is the timeline the LRCLIB lyrics and the cues are stamped on, so when a rehearsal take is saved, run synctoolbox's audio-to-audio pipeline once (tuning estimate, chroma + DLNCO at 50 Hz, chroma shift on 1 Hz CENS, MrMsDTW with step weights [1.5, 1.5, 2.0]) to map album time to rehearsal time, store the warping path, and convert lyric and cue timestamps across ([synctoolbox notebook](https://raw.githubusercontent.com/groupmm/synctoolbox/master/sync_audio_audio_full.ipynb); [synctoolbox utils](https://raw.githubusercontent.com/groupmm/synctoolbox/master/synctoolbox/dtw/utils.py)). The caveats from the same paper are the design constraints: results "depend heavily on which performance was chosen", so reject takes that are not full-length or align badly, and when two or three good takes exist run one OLTW per take and use the median (seven ran in real time on a 2015 laptop) ([ISMIR 2015](https://www.cp.jku.at/research/papers/Arzt_Widmer_ISMIR_2015.pdf)).

The concrete design is two trackers plus a confidence. The **fine tracker** at 50 fps runs OLTW on concatenated 12-bin L1-normalised log-compressed chroma and a 12-bin half-wave-rectified spectral-difference stream from a 2048-point STFT, band c = 500 frames (10 s), MaxRunCount 3, step weights (1, 1, 2), with the reference time axis pre-stretched by tapped_bpm / rehearsal_bpm so the expected path is diagonal (Arzt's tempo model does this continuously, cutting the misalignment rate from 41.8 % to 23.6 % on Schubert) ([Arzt & Widmer, SMC 2010](https://www.cp.jku.at/research/papers/Arzt_Widmer_SMC_2010.pdf)), and with JumpDTW-style transitions at part boundaries — repeat the current part, continue, skip up to six parts — which alone raised part-wise accuracy from 10.4 % to 28.3 % on mutilated opera ([Brazier & Widmer 2021](https://arxiv.org/pdf/2105.08531v1)). The **coarse tracker** every 300 ms matches the last 30 coarse frames (9 s) against every position in the song with free start and part-boundary jumps; its reliability flag is the slope of its last 30 positions lying in [0.8, 1.25] (Brazier's [0.5, 1.5] tightened to the band's tolerance), and while that flag held the coarse tracker alone was 98.9 % part-wise accurate ([Brazier & Widmer 2021](https://arxiv.org/pdf/2105.08531v1)). Confidence per emission combines the normalised-cost margin in the fine window, fine-path slope within [0.8, 1.25], fine/coarse agreement within ±1 bar, and input loudness above the silence floor; the follower emits `(position_s, rate, confidence)` every 100–200 ms. The part boundaries that make the jump sets are a seam gap: today the part map is computed in the browser (`app/src/songmap.ts`, `Part {kind, label, n, at, end}` from `m:ss part X` cue lines or inferred from the lyrics). The cleanest fix is to have the stage include its computed `parts`, the current `song`, the tapped BPM and the reference BPM in the state it already posts to `POST /api/stage/state`; the daemon caches them per song for the follower and for spoken cues, and falls back to parsing `part` cue lines from the gig text when no stage is open (losing only the lyric-inferred parts).

Planning numbers must be honest about their origin: every online alignment figure in the literature is classical. With a rehearsal reference and the usual arrangement, expect orchestral-class performance — 80–90 % of downbeats within 250 ms, ~98 % within 1 s — in steady sections, fine for lyrics and acceptable for effect cues fired from the smoothed clock ([ISMIR 2015, Table 7](https://www.cp.jku.at/research/papers/Arzt_Widmer_ISMIR_2015.pdf)); re-acquisition after a structural surprise takes 5–15 s (Arzt's medians 7–15 s; Brazier needs 30 coarse frames; Montecchio accepts only after a 15 s straight-line region) ([STAIRS 2010](https://www.cp.jku.at/research/papers/Arzt_Widmer_STAIRS_2010.pdf); [Montecchio & Cont, ISMIR 2011](https://archives.ismir.net/ismir2011/paper/000028.pdf)). The only pop data point is MATCH's informal note that two Beatles songs aligned across English and German versions, offline ([MATCH 2005](https://archives.ismir.net/ismir2005/paper/000002.pdf)). The first deliverable is therefore a measurement harness: record a rehearsal and a gig from the same interface, run the tracker offline in simulation, and score it against tapped bar markers before trusting it live. Guitar-only feeds need an explicit "no information" state — freeze the position update and emit confidence 0 when input RMS is below a floor or chroma flatness is high — mirroring the loudness-gated rest model that cut a particle filter's misalign rate from 14.3 % to 1.9 % on Mozart ([Korzeniowski et al., ICMC 2013](https://phenicx.upf.edu/system/files/publications/Korzeniowski_ICMC_2013.pdf)); improvised solos are marked free-running in the part map so the follower is advisory there and re-acquires at the next boundary.

### One clock, three owners, and voice as a re-seed

The ownership rules are the design: the **tap** owns the bar anchor and the restart gesture (beat_in_bar = 1, bar number from the part map, initial tempo and phase); the **beat tracker** owns tempo and beat phase, updated every beat with gain by confidence, and never touches the bar count on its own; the **position tracker** owns the coarse bar position and corrects the running count only when it disagrees by a whole bar for ≥2 consecutive bars; audio downbeat evidence is a vote that can raise or lower bar-phase confidence and trigger an "are we a bar out?" check, never a silent override, because at 46–57 % online downbeat F1 a silent override would be wrong almost half the time ([beat notes Q8](notes/beat_tempo_tracking.md)). The clock keeps a constant-velocity state (position, rate) with the tapped rate as its process model; tracker emissions are measurements whose variance scales with (1 − confidence)², so at confidence 0 the clock coasts exactly as it does today; the raw path is interpolated rather than smoothed, since Dixon found naive smoothing worsened results ([MATCH 2005](https://archives.ismir.net/ismir2005/paper/000002.pdf)); cues fire from the clock, never from raw tracker jumps. Handoff has hysteresis: the trackers take the clock only after confidence ≥0.7 has been sustained 3–5 s (Arzt judges a matcher only after ≥5 s of tracking ([STAIRS 2010](https://www.cp.jku.at/research/papers/Arzt_Widmer_STAIRS_2010.pdf))) and release it below 0.4 for 2 s; small disagreements under a bar are nudges, larger ones require the coarse tracker's reliability flag or a voice command; on loss the clock keeps the last good rate for ~2 bars, then falls back to the tapped rate and the view says "listening".

At the seam, this is concrete. `POST /api/stage {song, line, part, at, nudge, action, live}` requires an open stage and relays through `hub.emit`, and the browser's `songclock.ts` exposes `follow(at, rate, running)` with no confidence argument ([g3xn/daemon.py](../../g3xn/daemon.py); [app/src/songclock.ts](../../app/src/songclock.ts)). The daemon's new band clock should therefore publish a distinct WebSocket event — `clock` with `{at, rate, confidence, source, state}` at ≤5 Hz — and the stage view gains a confidence-gated follow: call `follow()` only in the FOLLOWING state, show "following" versus "on the clock" and the last confidently matched line otherwise, exactly the hold-and-resume UX that the better speech teleprompters converged on and that the follow products lack for bands ([VoicePrompter roundup](https://voiceprompter.app/blog/top-10-teleprompter-software.html); [Nakamura et al. 2015](https://arxiv.org/html/1512.07748v1)). Emitting the raw confidence rather than gating in the daemon is deliberate: the user designs the UI, and the confidence is what the screen must show. The pedal's own tap already reaches the daemon — `daemon.py` turns the `0x0A/0x02` setting echo into `{"type": "tempo", "bpm"}` — so it is the band clock's existing tap input ([g3xn/daemon.py](../../g3xn/daemon.py)). A voice correction is the same operation as Brazier's reset: on "chorus", "two bars behind" or "we're at '<line>'", compute the target reference frame from the part map or lyric line, set the fine tracker's accumulated-cost vector to +∞ except in a small window around target − 3 s (Arzt initialises a new matcher "a few seconds in the past" so it has context), clear the coarse tracker's history, and shorten the trust timer so the follower can retake control within 2–3 s once its slope and cost margin look right ([Brazier & Widmer 2021](https://arxiv.org/pdf/2105.08531v1); [STAIRS 2010](https://www.cp.jku.at/research/papers/Arzt_Widmer_STAIRS_2010.pdf)). The whole live path — one 2048-point FFT per 20 ms frame, a chroma fold, a 500-cell band update, a 30 × 800 coarse DP every 300 ms, plus the beat tracker's ~0.2 % — stays under ~10 % of one core, numpy-only, with no numba or torch in the daemon's live path ([alignment notes Q7](notes/live_alignment.md)).

## 3. Delays follow the band with one SysEx and a note-mode knob; listen to Link and MIDI clock before sending them

The pedal end is simpler than it looks because the protocol work is done. Zoom documents one tempo of **40–250 BPM** "used by every effect, rhythms and the looper", set by tap or knob, and the only MIDI statement in the entire manual is the specification row "USB: USB MIDI" — no implementation chart, no clock, no CC tap ([Zoom G3n/G3Xn manual](https://zoomcorp.com/media/documents/E_G3n_G3Xn.pdf)). Only the G11, which has DIN jacks, documents MIDI Clock in and out, and even it recognises neither Start/Stop nor Song Position, so Zoom's clock sync where it exists is tempo-only ([G11 manual](https://zoomcorp.com/media/documents/E_G11v2.pdf)); Singular Sound staff told a G1X Four owner that syncing to a BeatBuddy "does not seem to be possible" ([Singular Sound forum](https://forum.singularsound.com/t/sync-with-zoom-g1x4e/34530)). What the daemon already has is the reverse-engineered path: `Pedal.set_tempo(bpm)` sends settings target `0x0A` param `0x02` as a live edit, and the pedal sends the same message unsolicited when tapped ([g3xn/pedal.py](../../g3xn/pedal.py); [zoom-zt2](https://github.com/mungewell/zoom-zt2)). Two facts shape how to use it. First, tempo behaves as device-global: Zoom's sibling manuals call it the "master tempo", the SysEx lives under "system setting", and a scan of all 150 backed-up 736-byte patch images found no 8-bit field that could hold a BPM ([pedal notes KQ1](notes/pedal_and_band_tempo_sync.md)) — so the per-song tempo in a gig has to be pushed on every song change, and `set_tempo` has no reason to be confined to the scratch slot. In the code that is literally one flag: `Pedal._live(target, param, value, any_slot=False)` raises "live edits only run on the scratch slot" unless `any_slot=True`, which `stomp()` already passes and `set_tempo` does not ([g3xn/pedal.py](../../g3xn/pedal.py)); flip it once hardware test (b) below confirms the tempo survives a patch change. Second, a tempo push is slow and destructive at the wrong moment: settings apply ~0.4 s later and `_live` waits up to 1.0 s for the `64 03 01 0A` confirmation, changing the tempo "will erase the recorded phrase" of a playing loop, and older Zooms dropped delay buffers on tempo changes ([g3xn/pedal.py](../../g3xn/pedal.py); [Zoom manual p.37](https://zoomcorp.com/media/documents/E_G3n_G3Xn.pdf); [Looper's Delight archive](https://loopersdelight.com/LDarchive/201104/msg00195.html)). So push with hysteresis — only when the band clock's rounded BPM has changed by ≥1 and been stable for 1–2 s, at most every couple of seconds, never per beat, never while the looper is in use — and push the song's tempo on `POST /api/setlists/{gig_id}/load` and on every song select.

The knobs are where "delays follow the band" costs nothing new. Zoom's effect list marks Time on every delay except Pitch DLY, and Rate on Tremolo, Phaser, VinFLNGR, Vibrato, Slicer, WarpPhase, AutoPan, LoopRoll and PhaseDly, with the "tempo synchronization possible" icon ([Effects List](https://zoomcorp.com/documents/68/E_G5n_G3n_G3Xn_FX-list.pdf.pdf)); the catalog built from the pedal's own .ZD2 files shows those knobs have raw ranges above the printed ms/rate range — **23 surplus positions** on the 4000 ms delays (raw max 4022 vs 1–4000), **15** on the 2000 ms delays, **28** on the modulation rates, **10** on Tremolo, exactly **1** ("Sync") on SlapBackD, and **0** on every non-icon knob — and the harvested display table reads those positions as the pedal's note glyphs (Delay raw 4021/4022 show "♪x15"/"♪x16", Tremolo 109 "♪." and 110 "♪x2") ([pedal notes KQ4](notes/pedal_and_band_tempo_sync.md); [g3xn/data/effects.json](../../g3xn/data/effects.json)). The manual says the same in words: "set that parameter (Time or Rate, for example) to a note value (♪ or ♩)" ([Zoom manual p.44](https://zoomcorp.com/media/documents/E_G3n_G3Xn.pdf)). So the app parks Time or Rate on the wanted note position once — an ordinary knob write — and only ever pushes BPM; the pedal recalculates. The missing piece is a per-effect `note_positions` table in the catalog (which raw value is ♪, ♪., ♩ …), obtainable in one pass by sweeping the surplus raw values on the scratch slot and reading `Pedal.screen()`; the gig editor can then offer "dotted eighth" per song. Milliseconds are computed only for non-syncable knobs and pedals without sync: `ms = 60000 / BPM × beats`, `raw = round(ms) − display.offset`, clamped to the printed range (120 BPM dotted eighth = 375 ms → Delay raw 374). The most-reacted open request on the Fractal forum — "add BPM tempo option to each song in setlist ... to sync all delays when switching via setlist", 19 and 27 reactions, "under consideration" since 2022 — is exactly this, and g3xn can ship it before Fractal does ([Fractal forum, BPM in setlists](https://forum.fractalaudio.com/threads/bpm-tempo-in-setlists-songs.188635/)). Per-part tempo maps (Helix Stadium's Time flags) are the natural extension once the part map carries a tempo ([Helix Stadium Song View](https://manuals.line6.com/en/helix-stadium/live/song-view)).

Listening to the drummer's click is cheaper and more exact than any audio tracking, and it should sit above audio in the band clock's priority. **Ableton Link** shares tempo, beat and phase across devices on one network with automatic discovery; the current SDK is 4.1.1 (2026-10-19), dual-licensed GPLv2+/proprietary ([Ableton/link](https://github.com/Ableton/link); [releases](https://github.com/Ableton/link/releases)). Two Python bindings ship Windows wheels today: **aalink 0.2.3** (2026-07-03, GPLv3+, CPython 3.9–3.14 x86-64 and ARM64, asyncio-native with `tempo`, `beat`, `phase`, `playing`, `num_peers` and tempo/start-stop/peer callbacks, "aims to be punctual, but it is not 100 % accurate") and **LinkPython-extern 1.3.0** (2026-08-05, Unlicense binding that still embeds Link, wheels for 3.9–3.15; its GitHub link returned 404 during the research, so verify before depending on it) ([aalink on PyPI](https://pypi.org/project/aalink/); [aalink.cpp](https://github.com/artfwo/aalink/blob/HEAD/src/aalink.cpp); [LinkPython-extern on PyPI](https://pypi.org/project/LinkPython-extern/)). **Carabiner 1.2.0** exposes Link over a local TCP protocol from a separate process, which is the way to keep GPL code out of an MIT daemon's import graph ([Deep-Symmetry/carabiner](https://github.com/Deep-Symmetry/carabiner)). The payoff is the peer list: OnSong, Planning Center's metronome and Soundbrenner's app are Link peers, and Link metronomes align their downbeats to the shared beat ("the metronome starts on the next beat and aligns its downbeats") ([OnSong beat sync](https://onsongapp.com/docs/features/beatsync); [Planning Center](https://help.planningcenter.com/en/sync-the-metronome.html); [Soundbrenner listing](https://apps.apple.com/us/app/-/id1048954353)). The network caveat is hard: Link is UDP multicast on 224.76.78.75:20808 ([AbletonLinkProtocol](https://github.com/westhom/AbletonLinkProtocol)), Tailscale has "no support for broadcast or multicast due to the point-to-point nature of the connections" with the request open since 2020 ([Tailscale forum](https://forum.tailscale.com/t/broadcast-multicast-support/156); [tailscale #1013](https://github.com/tailscale/tailscale/issues/1013)), Ableton's troubleshooting page says Link does not work over a VPN (a search snippet; the page refused automated fetch), and venue and guest Wi-Fi commonly block device discovery — OnSong's own docs say "an isolated travel router can serve a stage" ([OnSong Ableton Link](https://www.onsongapp.com/docs/features/ableton-link); [Ableton Link troubleshooting](https://help.ableton.com/hc/en-us/articles/209073069)). Tailscale stays for the phone's HTTPS remote; Link needs a travel router or the laptop's hotspot. **MIDI clock in** needs only mido and ~50 lines in `footswitch.py`, which already owns the MIDI inputs: 24 ticks per beat, average intervals over one beat with outlier rejection because computer-generated clock jitters by several milliseconds per tick, take beat 1 from Start/Continue and Song Position when present, and report "no clock" after ~0.5 s of silence rather than freezing ([mido message types](https://mido.readthedocs.io/en/latest/message_types.html); [E-RM report](https://www.e-rm.de/data/E-RM_report_Jitter_02_14_EN.pdf)). That covers BeatBuddy (clock Always On or While Playing since firmware 1.85), Helix since 2.20, Quad Cortex since CorOS 2.3.0, and DAWs ([Singular Sound forum, fw 1.85](https://forum.singularsound.com/t/beatbuddy-firmware-update-control-how-drunk-your-beatbuddy-gets-and-more-version-1-85/3267); [Line 6 forum](https://line6.com/support/topic/59573-helix-as-midi-clock-source); [Neural DSP 2.3.0](https://neuraldsp.com/quad-cortex-updates/cortex-control-public-release-and-coros-2-3-0-are-now-available)). Which source wins must be explicit and visible — Link if a peer is present, else MIDI clock if ticks arrive, else audio, else the song's stored tempo — because silent reverts are the usual live failure: Helix drops back to the preset tempo when clock stops ([Line 6 forum](https://line6.com/support/topic/70308-when-helix-receives-midi-clock-tempo-changes-cause-delay-pitch-morphing-even-with-tap-tempo-pitch-set-to-transparent)).

Sending comes last and should be labelled honestly. MIDI clock out from Python over WinMM will be DAW-grade: with Ableton Live as master, the slave saw tempo wander 119.26–120.62 BPM, beat offsets with σ 2.28 ms and peaks to 8.99 ms, and cycle-to-cycle jitter σ 8.43 ms with extremes of −38/+22 ms over 13,500 ticks — setups that "would most probably fail a listening test", versus 400 ns on a hardware clock box ([E-RM report](https://www.e-rm.de/data/E-RM_report_Jitter_02_14_EN.pdf)). A dedicated thread scheduling ticks against `perf_counter()` with `timeBeginPeriod(1)` and above-normal priority will reach that grade and no better — and on Windows 11 the high resolution is not even guaranteed once the window is minimised or occluded ([timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)). Receivers' PLLs smooth that into a usable tempo, not a studio-tight phase, so ship it as an opt-in "lead the band's clock" extra and point players who need tighter phase at a Link-to-MIDI phone bridge or a clock box ([Link to MIDI](https://alexandernaut.com/linktomidi/)). Link *leading* (set `link.tempo` from the band clock) is the better send path for phones, since Link carries phase by design. Two platform notes bear on both directions: python-rtmidi 1.5.8 (2023) ships Windows wheels only for CPython 3.8–3.12, with 3.13/3.14 wheels sitting in unreleased PRs, so the gig laptop should stay on 3.12 ([python-rtmidi on PyPI](https://pypi.org/project/python-rtmidi/); [python-rtmidi #217](https://github.com/SpotlightKid/python-rtmidi/issues/217)); and this PC's build 26200 is Windows 11 25H2, on which Windows MIDI Services is in-box with WinMM "repointed to the new Windows Service" and multi-client access to every endpoint — which may make the memory note "close ToneLib before MIDI" obsolete, so it is a test (item 9 below), not a fact ([microsoft.github.io/MIDI](https://microsoft.github.io/MIDI/)). The lowest-risk click for a drummer without Link is still an audio click from the laptop into their in-ear feed: no network, fixed latency.

## 6. Nine hardware tests to run before writing tracker code

All pedal tests run on the scratch slot with ToneLib closed and the daemon connected; every one is ten minutes or less and most settle a decision in the roadmap.

## 7. Assumptions, gaps and risks: GPL, Python floors, Tailscale and thin pop/rock evidence

Licences need a decision now that the suite's own licence is known to be MIT ([LICENSE](../../LICENSE)). MIT code may depend on GPL libraries, but any distributed build that imports them is effectively GPL-bound, so aubio-ledfx (GPLv3), BTrack (GPLv3), essentia (AGPL) and aalink (GPLv3+) cannot be hard dependencies without constraining distribution; the numpy-only trackers avoid the problem for the live path, Carabiner keeps Link in a separate process, and LinkPython-extern's Unlicense binding still embeds Link's GPLv2+/proprietary code ([aubio-ledfx PyPI](https://pypi.org/pypi/aubio-ledfx/json); [aalink on PyPI](https://pypi.org/project/aalink/); [Ableton/link](https://github.com/Ableton/link)). madmom's source is BSD but its model files are CC BY-NC-SA 4.0 with commercial use requiring the author's permission, and whether running them at paid gigs is "non-commercial" is unresolved — a further reason not to depend on it ([madmom LICENSE](https://github.com/CPJKU/madmom/blob/main/LICENSE)). Demucs code is MIT while its weights' status is "an open legal question", Chordino is GPL, and Beat This!, matchmaker (Apache-2.0), synctoolbox and libfmp (MIT) and soxr (LGPL-2.1+) are clean ([demucs.net licensing](https://demucs.net/licensing); [python-soxr](https://github.com/dofuuz/python-soxr)). For a one-user tool none of this bites; it matters the day the repo is advertised.

Python versions are a minefield the roadmap must step around. The suite declares `>=3.10` and the repo venv runs 3.12 ([pyproject.toml](../../pyproject.toml)); **librosa 1.0.0 requires ≥3.12** while synctoolbox pins `librosa<1.0` and `numpy<2.5` ([librosa PyPI](https://pypi.org/pypi/librosa/json); [synctoolbox PyPI](https://pypi.org/pypi/synctoolbox/json)); aubio-ledfx requires ≥3.11; tempocnn stops below 3.12; pymatchmaker is `<3.14` with no Windows wheel; BeatNet hard-pins `numba==0.54.1` from 2021 and an unpinned madmom that resolves to the broken 0.16.1 sdist ([BeatNet PyPI](https://pypi.org/pypi/BeatNet/json)); python-rtmidi 1.5.8 has no cp313 wheel; and numba's Windows cp313/cp314 wheels were not verified. The practical rule is: pin the gig laptop to CPython 3.12, keep the daemon's live path on numpy plus the existing deps, and put every heavy or version-fragile tool (Beat This!, synctoolbox, librosa<1.0, torch, all-in-one, Demucs) behind an optional `[sync]` extra used only by the offline `prep-song` command. On 3.12 also remember that `time.monotonic()` is 15.6 ms-granular on Windows; the engine and the band clock must use `perf_counter()` ([capture notes Q8](notes/windows_audio_capture_recording.md)).

Several assumptions carry the whole design and are stated here so they can be tested rather than discovered. The audio interface's make is unknown: the measured latency (20–22 ms), the 10 ms block cadence and the auto-convert loss all come from a virtual Steam microphone, and whether `stream.latency` on a real UAC2 driver includes its USB buffering is unmeasured. Whether the drummer uses a click is unknown; the report covers both branches, and the honest statement is that with a click the audio beat tracker is a drift corrector, and without one it must carry ±10–15 % tempo movement and will lose lock in drumless intros and breakdowns until the drums return. Whether a second input channel exists for a room mic decides how good the beat tracker and follower can be; a guitar DI alone degrades both. The pedal's tempo is assumed global on the strength of Zoom's wording and the 150-image scan, which rules out a tempo inside the patch image but not a per-slot table elsewhere in flash; test 6 settles it. The per-effect "Tail" setting and the v2.0 OutputVP note are unconfirmed snippets. Handy Guitar Lab's support for the G3n family was not researched.

The evidence is thin where the project needs it most, and the roadmap's phase 0 exists because of that. Every online alignment number is classical piano, orchestra or opera; no benchmark exists for a live pop/rock band against a studio or rehearsal reference, and no source quantifies how vocals degrade chroma alignment in a band mix ([alignment notes Q8](notes/live_alignment.md)). The beat benchmark is synthetic — perfectly regular strums, no bleed, no vocals — and no published comparison of "comb filter with a strong prior" against RNN trackers exists; the claim that the prior closes most of the 57 → 75 F1 gap for drummed pop/rock is inference ([beat notes Q6](notes/beat_tempo_tracking.md)). No source quantifies online downbeat lock-in time, phase-flip frequency, click-versus-no-click accuracy, or recovery after a break. The alignment thresholds (take control at 0.7, release at 0.4, slope bounds, Arzt's r = 2 and s = 10) were tuned on classical data and are starting points. The `inputBufferAdcTime` behaviour is an observation on one PortAudio build; pycaw's COM threading beside uvicorn and pywebview is untested; GIL contention with faster-whisper is unmeasured; the FLAC ratio on a real 24-bit band mix is unmeasured (plan on 55–80 % of WAV); iOS Safari's handling of 24-bit WAV and Ogg/Opus in `<audio>` is unsourced, so AAC-m4a and MP3 are the safe phone formats.

Networking and automation risks have cheap mitigations that should be defaults. Link cannot cross Tailscale or any VPN and is often blocked by venue Wi-Fi client isolation, so the stage needs a travel router or a laptop hotspot and the UI must show which clock source is live, because Helix-style silent reverts are the common failure ([Tailscale forum](https://forum.tailscale.com/t/broadcast-multicast-support/156); [OnSong Ableton Link](https://www.onsongapp.com/docs/features/ableton-link)). Any automatic pedal action driven by a clock — tuner mute, patch switch, cue — defaults to arm-and-prompt when confidence is below threshold, because the one documented automatic tuner-mute "ends up muting while I'm playing, and unmuting during silent sections" ([Neural DSP thread](https://unity.neuraldsp.com/t/how-do-you-set-your-tuner-midi-control-up-from-your-daw/9959)). Tempo pushes erase a playing loop and may glitch delays, so they wait for settled changes and never happen while the looper runs ([Zoom manual p.37](https://zoomcorp.com/media/documents/E_G3n_G3Xn.pdf)). Band-page sync at half-second latency is fine for "which song" and useless for cues, which stay local to the daemon ([BandHelper linking](https://www.bandhelper.com/tutorials/linking_devices.html)). And the recordings directory grows at a gigabyte an hour until the post-song FLAC exists; the preflight's disk-space check and a retention policy (keep FLAC, drop WAV once verified) are part of phase 1, not an afterthought.

## Conclusion

The research reframes "band syncing" from a tracking problem into an ownership problem. The pedal already receives tempo and already reports taps, the knobs already have note modes, the stage already has a clock with a `follow()` seam, and the best alignment reference the literature knows about — a recording of the same players on the same gear — is something the band can make at its next rehearsal once the daemon records. What was missing was not an algorithm but a single audio engine that owns the interface and a band clock that owns the decision of who to believe. Once those exist, the trackers are confidence-weighted advisors that can be added, measured and turned off independently, and phases 1 and 2 alone (record every show, push every song's tempo into tempo-synced delays) deliver the features gigging guitarists ask modeler vendors for most.

The second shift is in what "usable at real gigs" means. The surveyed ecosystems automate the timeline (BandHelper's durations, Playback's cues, Helix Stadium's flags) and none of them listen to the band; the prompter products that do listen all fail silently. g3xn's advantage is that its fallback — the two-bar tap, voice corrections, the part map — is already better than those products' primary mode, so the automatic layer only ever has to be *better than nothing when confident and invisible when not*. Holding to that rule, plus a preflight that refuses to let the show start with a stale backup or a starving USB port, is worth more at the first gig than any tracker accuracy figure in this report.
