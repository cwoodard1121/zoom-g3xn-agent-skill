## Q1. Which Windows host API to use through sounddevice/PortAudio (MME, DirectSound, WASAPI, WDM-KS, ASIO), shared vs exclusive WASAPI, sample rates, channels, latency, pitfalls

### Takeaway
Use **WASAPI shared mode at the interface's Windows mix rate** (set the interface's "Default Format" to 48 kHz in Windows Sound settings), `WasapiSettings(exclusive=False, auto_convert=False)`, `blocksize=0`, float32, all input channels, default `latency='high'`. The 0.5.6 wheel bundles MME, DirectSound, WASAPI and WDM-KS by default and a second DLL with ASIO that is enabled only by setting `SD_ENABLE_ASIO` before import; ASIO and WDM-KS are single-client, exclusive mode seizes the endpoint and silently starves every other stream on it, and MME gives no timestamps and truncates names to 31 characters.

### Cited Findings
- Host APIs in the bundled DLLs: "Default builds (libportaudio32bit.dll, libportaudio64bit.dll, libportaudioarm64.dll) include MME, DirectSound, WDM/KS, and WASAPI"; the `*-asio.dll` builds add ASIO — [spatialaudio/portaudio-binaries README](https://github.com/spatialaudio/portaudio-binaries). Verified on the dev PC: `sd.query_hostapis()` lists MME, Windows DirectSound, Windows WASAPI, Windows WDM-KS (no ASIO) by default.
- ASIO switch: "pip install provides two PortAudio DLLs, one with ASIO support and one without"; the non-ASIO DLL loads by default "due to problems described in issue #496"; set the environment variable `SD_ENABLE_ASIO` (any value) *before* importing sounddevice; works only for pip installs and not when a custom `portaudio.dll` is on `%PATH%` — [sounddevice installation docs](https://python-sounddevice.readthedocs.io/en/0.5.6/installation.html). Verified on the dev PC: with `SD_ENABLE_ASIO=1` the host API list becomes MME, DirectSound, **ASIO**, WASAPI, WDM-KS (0 ASIO devices here: no ASIO driver installed); the package directory holds `libportaudio64bit.dll` and `libportaudio64bit-asio.dll` (plus 32-bit and arm64 pairs); the loader code is `if 'SD_ENABLE_ASIO' in _os.environ: _libname = 'libportaudio' + _platform_suffix + '-asio.dll'`.
- Why ASIO is off by default: importing an ASIO-built PortAudio "momentarily interrupted audio already playing in other applications, but only when exclusive mode was enabled on the default device", and a Realtek ASIO driver added "an import delay of at least one second"; maintainer mgeier: "I think that's a good reason to deactivate ASIO by default"; fixed in 0.5.0 (2024-08-11) — [python-sounddevice issue #496](https://github.com/spatialaudio/python-sounddevice/issues/496).
- Version history: 0.5.0 (2024-08-11) "Remove ASIO support from bundled DLLs"; 0.5.1 (2024-10-12) "bundle both non-ASIO and ASIO DLLs, the latter can be chosen by defining the SD_ENABLE_ASIO environment variable"; 0.4.7 (2024-05-27) "support paWinWasapiAutoConvert with auto_convert flag"; 0.5.3 (2025-10-19) "add explicit_sample_format parameter to WasapiSettings"; 0.5.4 (2026-01-21) Windows ARM64 wheels; 0.5.6 (2026-08-17) current — [sounddevice version history](https://python-sounddevice.readthedocs.io/en/0.5.6/version-history.html).
- `WasapiSettings(exclusive=False, auto_convert=False, explicit_sample_format=False)`: exclusive "allows to deliver audio data directly to hardware bypassing software mixing"; auto_convert lets WASAPI "insert a system-level channel matrix mixer and sample rate converter", is "required for streams that don't match the system mixer sample rate" and "applies only in shared mode"; explicit_sample_format makes opening fail if the format is unsupported by the hardware (exclusive) or mixer (shared). `AsioSettings(channel_selectors)` opens only the listed zero-based channels; the list length must match `channels` or it "may result" in a crash — [sounddevice platform-specific settings](https://python-sounddevice.readthedocs.io/en/0.5.6/api/platform-specific-settings.html). Verified on the dev PC: `inspect.signature(sd.WasapiSettings.__init__)` = `(self, exclusive=False, auto_convert=False, explicit_sample_format=False)`.
- Shared-mode rate restriction, verified on the dev PC with `sd.check_input_settings`: the WASAPI entry reports `default_samplerate` 44100 (its mix format); 16 000, 48 000 and 96 000 Hz fail with `Invalid sample rate [PaErrorCode -9997]` in shared mode, succeed with `auto_convert=True`, and succeed in exclusive mode; MME, DirectSound and WDM-KS accept every rate (Windows resamples for them). This matches the long-standing issue that in WASAPI shared mode "it is necessary to match the samplerate in sounddevice and Control Panel > Sound > device > Properties > Advanced tab > Default Format" — [python-sounddevice issue #52](https://github.com/spatialaudio/python-sounddevice/issues/52).
- PortAudio's own WASAPI notes: event-driven exclusive latency "about 3 ms" (lowest on HD Audio chips); in shared mode latency "can not be lower than 20 ms"; polling mode 10–13 ms; too little latency in shared mode "distorts audio" — [pa_win_wasapi.h](https://github.com/PortAudio/portaudio/blob/master/include/pa_win_wasapi.h).
- Exclusive mode semantics from Microsoft: "Exclusive-mode streams seize the audio endpoint—all system sounds, notifications, and audio from other applications are silenced"; default endpoint settings are that exclusive use is allowed and "a request ... to play or record an exclusive-mode stream preempts any shared-mode stream"; the user can clear "Allow applications to take exclusive control of this device" / "Give exclusive mode applications priority" per device; Windows 10+ `IAudioClient3` gives shared-mode periods "as low as" the engine minimum, "latency comparable to exclusive mode while preserving system sound mixing" — [Microsoft Learn, Exclusive-Mode Streams](https://learn.microsoft.com/en-us/windows/win32/coreaudio/exclusive-mode-streams).
- Verified on the dev PC (same physical device, PortAudio entries MME #1 / WASAPI #21 / WDM-KS #25): an existing MME 16 kHz stream plus a new WASAPI **exclusive** 48 kHz stream: the exclusive one opened fine and the MME stream received exactly one more callback flagged `input overflow` and then nothing (silent stall, no exception); exclusive first then MME: `Device unavailable [PaErrorCode -9985]`; WASAPI shared 44.1 k then exclusive 48 k: the shared stream got 1 callback and stalled; WDM-KS 48 k then MME 16 k: `Device unavailable [-9985]`. This is the documented preemption behaviour ("a request ... to take exclusive control of the device succeeds if ... the device is being used in shared mode", and exclusive-mode streams "seize the audio endpoint") — [Microsoft Learn, Exclusive-Mode Streams](https://learn.microsoft.com/en-us/windows/win32/coreaudio/exclusive-mode-streams).
- Windows audio engine buffering: "by default all applications in Windows 10 and later will use 10-ms buffers to render and capture audio"; before Windows 10 the capture buffer "was always set to 10 ms"; capture-side APOs (audio effects) run in the engine path and "The latency of the APOs varies"; exclusive mode "bypasses the audio engine" but then "no other application can use that endpoint" — [Microsoft Learn, Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio). Verified on the dev PC: WASAPI shared callbacks arrive in 480-frame (10 ms) blocks at 48 kHz and 441-frame blocks at 44.1 kHz with `blocksize=0`; reported `stream.latency` 0.022 s shared, 0.020 s exclusive, 0.030 s MME (16 kHz/480), 0.085 s WDM-KS (4096-frame blocks); `cpu_load` 0.002–0.010.
- Class-compliant interfaces need no vendor driver: "Starting with Windows 10, release 1703, a USB Audio 2.0 driver is shipped with Windows" (`usbaudio2.sys`, WaveRT); "If a partner driver exists ... that driver is installed and overrides the class driver"; "an arbitrary number of channels, greater than eight, aren't supported in shared mode"; ASIO is a separate third-party model that "utilizes exclusive mode" — [Microsoft Learn, USB Audio 2.0 Drivers](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/usb-2-0-audio-drivers) and [Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio).
- The PortAudio default host API "will be the lowest common denominator host API on the current platform and is unlikely to provide the best performance" — [PortAudio portaudio.h docs](https://www.portaudio.com/docs/v19-doxydocs/portaudio_8h.html). Verified on the dev PC: `sd.default.hostapi` is 0 = MME, so `device=None` (what `LaptopMic`/`WakeListener` pass today) opens the MME entry, and `voice.microphones()` lists only MME names.
- MME names are truncated: MME's `WAVEINCAPS.szPname[MAXPNAMELEN]` holds the "Product name in a null-terminated string" — [Microsoft Learn, WAVEINCAPS](https://learn.microsoft.com/en-us/windows/win32/api/mmeapi/ns-mmeapi-waveincaps). Verified on the dev PC: the MME entry is `'Microphone (Steam Streaming Mic'` (31 chars, cut mid-word) while the WASAPI entry is `'Microphone (Steam Streaming Microphone)'`; one physical device appears 6 times across host APIs (and the WASAPI entry reports 1 input channel where MME/WDM-KS report 8).
- Timestamps per host API, verified on the dev PC: MME callbacks report `inputBufferAdcTime = currentTime = 0.0`; WDM-KS reports a *relative* ADC time starting at 0; only WASAPI reports absolute times on the `Stream.time` clock (see Q8). Field meanings per [sounddevice streams docs](https://python-sounddevice.readthedocs.io/en/0.5.6/api/streams.html).
- No channel selector exists for WASAPI in sounddevice: `WasapiSettings` has only `exclusive`, `auto_convert`, `explicit_sample_format`, while channel selection is offered only by `AsioSettings(channel_selectors)` and `CoreAudioSettings(channel_map)` — [sounddevice platform-specific settings](https://python-sounddevice.readthedocs.io/en/0.5.6/api/platform-specific-settings.html); `channels=N` opens the first N inputs ("ranges from 1 to the device's max input ... channels") — [sounddevice streams docs](https://python-sounddevice.readthedocs.io/en/0.5.6/api/streams.html).
- Callback status flags: `paInputOverflow` "indicates that data prior to the first sample of the input buffer was discarded due to an overflow"; `paInputUnderflow` means input is "all silence (zeros) because no real data is available" — [PortAudio portaudio.h docs](https://www.portaudio.com/docs/v19-doxydocs/portaudio_8h.html); exposed as `status.input_overflow` / `status.input_underflow` on the sounddevice `CallbackFlags` object (verified in the installed sounddevice.py).

### Inferences
- The engine should open exactly one WASAPI shared stream on the interface at its mix rate. Shared mode is the only mode in which the daemon, the browser's `getUserMedia` scope (Chrome uses shared WASAPI) and a wake-word stream can all read the same interface; exclusive mode or WDM-KS would stall the others without raising anything (the stall is only visible as a callback that stops arriving).
- Match the rate instead of using `auto_convert`: on the dev PC the auto-convert path lost 2.6–6 % of samples with no overflow flag (details in Q5), while shared-at-mix-rate, exclusive and WDM-KS delivered 100 %. Put the interface's Windows Default Format at 48 kHz/24-bit once, then read `sd.query_devices(dev)['default_samplerate']` at start and open at exactly that rate; resample inside the daemon (soxr) for anything that wants another rate (16 kHz for whisper).
- ASIO buys nothing for this use (recording + analysis, not low-latency monitoring) and costs the shared-mode coexistence; leave `SD_ENABLE_ASIO` unset. If a vendor ASIO driver is ever wanted, the env var must be set before the lazy `import sounddevice` in voice.py, and `AsioSettings(channel_selectors=[...])` must list exactly `channels` entries.
- Keep `latency='high'` (sounddevice's default; "more robust against buffer under- and overflows" per the streams docs) and `blocksize=0`; nothing in the pipeline needs fixed 10 ms blocks except the wake listener, which can be re-framed after resampling.
- Turn off Windows "audio enhancements"/signal processing on the interface's recording endpoint: shared-mode capture passes through the capture APOs (noise suppression etc. would be baked into the recording). sounddevice does not expose PortAudio's WASAPI "raw" stream option, so this has to be done in Windows Sound settings.

### Gaps
- No real USB interface was available on the dev PC, so the measured latencies (20–30 ms) and the auto-convert sample loss come from a virtual Steam device; both need re-measuring on the actual interface.
- I did not find a source stating which PortAudio commit the 0.5.6 DLLs were built from ("revision unknown" at runtime; the README does not say).
- Whether PortAudio's WASAPI backend uses `IAudioClient3` low-period shared streams on Windows 10/11 was not verified (not needed for recording).

## Q2. Can two Python streams open the same device at once, and what is the recommended one-capture-stream architecture (tee to disk writer, analysis ring buffers, 16 kHz wake-word copy), Python patterns, CPU cost

### Takeaway
Two shared-mode streams on one device do coexist (verified: MME 16 kHz + WASAPI 48 kHz, and two WASAPI shared streams, for 3 s and for 90 s with zero overflows), but they are two independent, differently-delayed copies and exclusive/WDM-KS/ASIO break the arrangement, so build **one** native-rate capture stream whose callback only copies the block into a `queue.SimpleQueue` (writer thread) and a numpy ring buffer (analysis), with a soxr `ResampleStream` producing the 16 kHz mono feed for `WakeListener.feed()`; the whole tee costs well under 2 % of one core.

### Cited Findings
- Coexistence verified on the dev PC: "MME 16 k + WASAPI shared(auto_convert) 48 k, same device": both ran 3 s with 0 overflows; "two WASAPI shared streams 16 k + 48 k": both ran, 0 overflows; "WASAPI shared 44.1 k (native) + MME 16 k": both ran, 0 overflows. The 90-second engine prototype (WASAPI 48 k capture → SimpleQueue → soundfile WAV writer + soxr 16 k resampler + 10 s ring buffer, with an MME 16 kHz stream open beside it) finished with callbacks=8450, overflows=0, queue depth never above 2 items, `cpu_load` 0.005–0.010, callback blocks always 480 frames. Mechanism: shared mode is designed so that "several applications can share an audio endpoint device by opening shared-mode streams on the device" — [Microsoft Learn, Exclusive-Mode Streams](https://learn.microsoft.com/en-us/windows/win32/coreaudio/exclusive-mode-streams).
- Callback rules: it must not "allocate memory, access the file system, call library functions, or call blocking functions"; apart from `cpu_load`, "PortAudio API calls are not permitted inside the callback"; exceptions other than `CallbackStop`/`CallbackAbort` print a traceback and stop the callback from being called again; "For heavy CPU use, blocksize=0 gives the most robust behavior" — [sounddevice streams docs](https://python-sounddevice.readthedocs.io/en/0.5.6/api/streams.html).
- The canonical pattern is the project's own example: the callback does `q.put(indata.copy())` "(from a separate thread) for each audio block" and the main loop does `file.write(q.get())` inside `sf.SoundFile(...)`, opening the file before the stream starts — [sounddevice examples, rec_unlimited.py](https://python-sounddevice.readthedocs.io/en/0.5.6/examples.html).
- `Stream.time` "increase[s] monotonically with an unspecified origin", is "valid from open until close", and shares its clock with the callback timestamps; `Stream.latency` "provides the most accurate estimate of input/output latency available to the implementation"; `Stream.cpu_load` is the fraction of CPU used by the stream's processing including the callback — [sounddevice streams docs](https://python-sounddevice.readthedocs.io/en/0.5.6/api/streams.html).
- Resampling cost measured on the dev PC (30 s of 48 kHz stereo → 16 kHz mono in 1024-frame chunks): `soxr.ResampleStream` QQ 0.19 %, LQ 0.29 %, MQ 0.38 %, HQ 0.36 %, VHQ 0.41 % of one core; `scipy.signal.resample_poly(x, 1, 3)` on the whole buffer 0.16 % (batch only; a streaming version needs its own filter-state handling). python-soxr: `soxr.ResampleStream(in_rate, out_rate, channels, dtype='float32')`, `resample_chunk(x, last=eof)`, "Output frame counts can vary between chunks, and leading zeros in the output are normal"; dtypes float32/float64/int16/int32; input `[frame, channel]`; LGPL-2.1-or-later; patch notes dated 2026-05-22 — [python-soxr](https://github.com/dofuuz/python-soxr).
- Disk-write cost measured on the dev PC (soundfile, 30 s stereo 48 kHz in 4800-frame writes): WAV PCM_24 0.33 % of one core, FLAC PCM_24 0.85 %, FLAC PCM_16 0.71 % (see Q3 for sizes).
- faster-whisper's PyAV is already able to resample: voice.py's `decode()` uses `av.AudioResampler(format='s16', layout='mono', rate=16000)` (project source, g3xn/voice.py), and the installed PyAV 19.0.2 exposes encoders libopus, libmp3lame, flac, aac, pcm_s24le (verified on the dev PC; libvorbis is absent).

### Inferences
- Engine skeleton (all numbers verified in engine.py on the dev PC):
  ```python
  q = queue.SimpleQueue()                       # callback -> writer/analysis thread
  ring = np.zeros((sr*PREROLL_S, ch), 'float32') # native-rate ring; pre-roll AND analysis read it
  def cb(data, frames, tinfo, status):
      if status.input_overflow: stats.overflows += 1
      q.put((data.copy(), tinfo.currentTime, stats.frames))   # no allocation besides the copy
      write_ring(data); stats.frames += frames
  stream = sd.InputStream(device=dev_index, samplerate=mix_rate, channels=n_in, dtype='float32',
                          blocksize=0, callback=cb, extra_settings=sd.WasapiSettings())
  ```
  Writer thread: `data, t, idx = q.get()` → `wav.write(data)` → `mono16 = rs.resample_chunk(data[:, voice_ch])` → re-frame into 480-sample blocks → `WakeListener.feed(frame)`; analysis consumers (beat tracker, meters) read the ring buffer on their own cadence instead of being in the callback.
- `WakeListener.feed` already assumes 30 ms frames at 16 kHz and `LaptopMic.stop()` returns 16 kHz mono; both can be fed from the engine's 16 kHz tap, so the existing `sounddevice.InputStream` calls in voice.py become one subscription on the engine when the voice mic is the interface. When the voice mic is a *different* physical device (laptop mic, wireless receiver into the laptop), keep a second stream on that device: two devices never conflict.
- Use `queue.SimpleQueue` (reentrant, no `maxsize`) or `queue.Queue(maxsize=~200)` with `put_nowait` and a dropped-block counter; never a Python list that grows for the whole show (`LaptopMic._chunks` is fine for a few seconds of push-to-talk, not for 3 hours).
- Threads, not asyncio, for the audio side: the callback is already on a PortAudio thread, soundfile/soxr/PyAV release the GIL in C, and the FastAPI loop only needs periodic stats (levels, overflow counts, file names) pushed through the WebSocket hub from the writer thread via `loop.call_soon_threadsafe`.
- Budget: capture + copy + 24-bit WAV write + soxr HQ 16 kHz + per-block RMS is roughly 1–2 % of a core; live Opus/AAC encoding would add 3–4 % (Q3) and is better done after each song closes.

### Gaps
- GIL contention from faster-whisper (CTranslate2 int8 on CPU) running at the same time was not measured; the 90 s prototype had no transcription load. The overflow counter and `cpu_load` should be logged during a real "Hey Claude" transcription to confirm the WASAPI host buffer (~20 ms) absorbs it.
- My RSS measurement in engine.py was broken (ctypes struct returned 0), so no empirical memory-growth number; the design is bounded by construction (fixed ring, bounded queue, streaming file writes).

## Q3. Recording to disk: libraries and formats (WAV/RF64/FLAC via soundfile, Opus/MP3/AAC via PyAV), sizes per hour, 24-bit vs float32, crash-safety, browser-friendly outputs

### Takeaway
Record live to **plain WAV PCM_24 at the native rate with python-soundfile** (≈1.04 GB/h stereo 48 kHz; a crashed WAV read back intact with both libsndfile and ffmpeg in my test), never RF64 or FLAC as the *live* format (a crashed RF64 read as 0 frames; a crashed FLAC was unreadable by libsndfile and ffmpeg recovered all but the last 2432 samples); after a song file closes, transcode in a worker with the already-installed PyAV to FLAC for the archive and to AAC-m4a (`movflags=faststart`) or MP3 for the ghost band, since no ffmpeg CLI is on the machine.

### Cited Findings
- soundfile 0.14.0 released 2026-06-06, wheels `py2.py3-none-win_amd64` (+ win32, win_arm64), requires Python ≥ 3.10; 0.13.0 moved to libsndfile 1.2.2 — [soundfile on PyPI](https://pypi.org/project/soundfile/). Verified on the dev PC: `sf.__libsndfile_version__ == '1.2.2'` in 0.14.0.
- Streaming write API: open with mode `'w'` (or `'x'` to refuse overwriting), `write()` appends at the current position, "Data written with write() is not immediately written to the file system but buffered in memory", `flush()` pushes it, `close()`/context manager finishes; subtypes include PCM_16 (WAV default), PCM_24, FLOAT; FLAC/OGG/MP3 supported, `compression_level` 0.0–1.0 for compressed formats — [python-soundfile docs](https://python-soundfile.readthedocs.io/en/latest/).
- Sizes and write cost measured on the dev PC (stereo 48 kHz, 30 s synthetic music-like signal, extrapolated): WAV PCM_16 691 MB/h; WAV PCM_24 1037 MB/h (0.33 % core); WAV FLOAT 1382 MB/h; RF64 PCM_24 1037 MB/h; FLAC PCM_16 465 MB/h (0.71 % core); FLAC PCM_24 811 MB/h (0.85 % core); PyAV flac 819 MB/h (0.40 %). Arithmetic check: 48 000 × 2 ch × 3 B × 3600 s = 1.037 GB/h.
- FLAC on real music "can typically be reduced to between 50 and 70 percent of its original size"; levels 0–8 trade encode speed for ratio and beyond level 5 encoding "takes considerably more time" for "little space saved"; each frame is independent with a sync word, so FLAC "supports fast seeking" and streaming — [Wikipedia, FLAC](https://en.wikipedia.org/wiki/FLAC). (xiph.org has removed its comparison page and the Hydrogenaudio wiki returned 403.)
- Crash-safety measured on the dev PC (child process writes 5 s with soundfile, then `os._exit(1)` without closing): **WAV PCM_24**: header fields left as RIFF size 8 and data size 0, yet `sf.info` reports 240 000 frames and PyAV/ffmpeg decodes 240 000 frames (both treat data size 0 as "to end of file"); calling `flush()` or libsndfile's `SFC_SET_UPDATE_HEADER_AUTO` (0x1031) via `soundfile._snd.sf_command` changed nothing (header fields still 8/0). **RF64 PCM_24**: `ds64` chunk left with data64 = 0 → libsndfile sees 0 frames, ffmpeg decodes 0 frames. **FLAC PCM_24**: libsndfile fails (reports 2^63−1 frames), ffmpeg decodes 237 568 of 240 000 frames. Properly closed WAV has correct sizes (RIFF 8 640 036 / data 8 640 000 for 30 s).
- PyAV encoders verified on the dev PC (30 s stereo 48 kHz): libopus 96 kb/s → 59 MB/h, 4.2 % of one core as `.opus` (11 % as `.ogg`); libmp3lame 160 kb/s → 72 MB/h, 2.0 %; aac 160 kb/s → 75 MB/h, 3.5 %; flac → 819 MB/h, 0.4 %. Working pattern: `out = av.open(path, 'w', options={'movflags': 'faststart'})`, `st = out.add_stream('aac', rate=48000)`, `st.codec_context.format = 'fltp'; st.codec_context.layout = 'stereo'; st.codec_context.bit_rate = 160000`, frames built with `av.AudioFrame.from_ndarray(block.reshape(1, -1), format='flt', layout='stereo')` + `frame.sample_rate`, `frame.pts` (running sample count), `frame.time_base = Fraction(1, 48000)`, `for pk in st.encode(frame): out.mux(pk)`, then `st.encode(None)` and `out.close()`. With `movflags=faststart` the `moov` atom lands at byte 32 before `mdat` (default: `moov` at the end); the MP3 output carries an Xing/Info header; all three read back with the right duration.
- FFmpeg-style formats for the ghost band: the project already serves `~/.g3xn/tracks/<song-key>/track.<ext>` with HTTP Range requests for mp3/m4a/ogg/wav/webm/flac (task brief); no `ffmpeg` executable is on `%PATH%` on the dev PC (verified).

### Inferences
- Live format = WAV PCM_24 at the mix rate (float32 capture → libsndfile converts). Float32 WAV costs 33 % more for no benefit in shared mode (the engine's float path is already clamped); 16-bit throws away the interface's 24-bit headroom and only saves 33 %.
- A 4 GB WAV holds 4.1 h at 48 kHz/24-bit stereo (3.1 h at float32, 4.5 h at 44.1 kHz) — enough for a show, but do not rely on it: the per-song splitter (Q4) keeps every file far below the limit, and the "full show" is the ordered list of segments (write a `show.json` manifest), not one giant file. If one continuous file is wanted anyway, roll it every 60 min; avoid RF64 (crash-unsafe here).
- Startup repair: on daemon start, scan the recordings directory for WAVs whose RIFF/data size fields are 8/0 (or smaller than the file) and patch them: write `struct.pack('<I', file_size - 8)` at offset 4, locate the `data` chunk header by walking the RIFF chunks (libsndfile headers are not always 44 bytes), and write `struct.pack('<I', file_size - data_offset - 8)` into its size field; libsndfile and ffmpeg tolerate the placeholder but other players may not. If the engine writes its own WAV (header + raw `pcm_s24le` bytes via `os.write`), it can `pwrite` the two size fields every few seconds for free, which makes even the in-progress file valid.
- Post-song pipeline (worker thread, after `close()`): FLAC via soundfile or PyAV for the archive (~50–70 % of WAV on real music), AAC m4a with faststart (or MP3) for the ghost band and for the phone: 1 GB/h WAV over Tailscale to a phone is impractical, 60–75 MB/h is fine. Keep the WAV until the FLAC exists, then delete it or keep both by policy.
- Browser seeking: m4a with `moov` first and MP3 with an Xing header give `<audio>` the duration immediately and seek with Range requests; FLAC and WAV also seek; Opus in Ogg works in Chrome/Firefox but Safari support is version-dependent (unverified, see gaps).

### Gaps
- No measurement of FLAC ratio on an actual band mix at 24-bit (my synthetic signal gave 78 % for 24-bit vs 67 % for 16-bit, which is not representative); plan on 55–80 % of WAV.
- Whether iOS Safari (the phone UI) plays 24-bit WAV and Ogg/Opus from `<audio>` was not sourced; AAC-m4a and MP3 are the safe assumption.
- The soundfile docs do not state how libsndfile handles a WAV that grows past 4 GB in `'w'` mode (auto-RF64 or error); test before relying on single-file shows.
- Why `SFC_SET_UPDATE_HEADER_AUTO` left the WAV header untouched in my test (the child's return value was lost at `os._exit`) was not investigated.

## Q4. Per-song splitting with pre-roll and post-roll, file naming, keeping the full show, and how recorders/DAWs do it

### Takeaway
Keep the capture stream and a native-rate ring buffer running for the whole show; on the stage's *song-change* event (not raw patch changes), start the next file by first dumping the last N seconds of the ring (pre-roll) and keep the previous file open for M more seconds (post-roll); name files by date/gig/order/song-key and write a manifest so the show is the ordered set of segments. Field recorders do exactly this with a DSP buffer (Zoom H6 Pre Rec = 2 s; MixPre-6 II reportedly up to 10 s).

### Cited Findings
- Zoom H6 "Pre Rec": "By setting the recorder to constantly capture the input signal, you can start recording two seconds before pressing the button"; "The Auto Rec and Pre Count functions cannot be used at the same time as this function" — [Zoom H6 operation manual, p. 27 (manualslib)](https://www.manualslib.com/manual/2621329/Zoom-H6.html?page=27). A Zoom rep answer quoted on a forum says the buffer "is kept in a data buffer within the DSP of the unit" and its length "varies depending on WAV settings" — [DVXuser "Ask a Zoom rep"](https://www.dvxuser.com/threads/ask-a-zoom-rep.357172/page-4) (second-hand; search snippet, page not fetched).
- Sound Devices MixPre-6 II pre-record "up to 10 seconds" with "no post-record" — only found in a customer review — [Thomann review page](https://www.thomann.fr/sound_devices_mixpre_6_ii_reviews.htm) (weak source; the sounddevices.com product page returned 403).
- The ring buffer already needed for analysis serves pre-roll: python-soxr and PortAudio impose nothing here; the 90 s prototype on the dev PC kept a 10 s native-rate ring (`np.zeros((sr*10, ch), 'float32')`, ~3.8 MB for stereo) updated in the callback with a two-slice wrap-around copy at zero measurable cost (`cpu_load` ≤ 0.01).
- The stage knows the current song and song changes driven by the pedal's patch changes, and has a song clock; recordings are stored per song key under `~/.g3xn/tracks/<song-key>/` (task brief / project).

### Inferences
- Splitter design (writer thread owns all files):
  ```python
  on_song_change(new_song, t_event):            # from the stage, debounced (a song can span patches)
      old = current; current = Segment(new_song, t_event)
      current.file = open_wav(path_for(new_song))
      current.file.write(ring.last(PREROLL_S))   # pre-roll: last 5–10 s already captured
      old.close_after(POSTROLL_S)                # keep writing old for 3–5 s more, then close -> post-process
  ```
  Overlapping 10–15 s between consecutive files is intended (a song's intro belongs to it even if the guitarist switched patches late). Between-song chatter can be its own "gap" segment so the full show is lossless.
- Pre-roll length: 5–10 s covers "the drummer counted in before I stepped on the patch"; keep the ring at 2× that so analysis can also look back.
- Naming: `~/.g3xn/recordings/<YYYY-MM-DD>_<gig-slug>/<NN>_<song-key>_<HHMMSS>.wav` plus `<same>.json` (song key, gig, wall start time, `perf_counter` and ADC time of the first sample, pre-roll seconds, device name, rate, channels, overflow count) and a `show.json` manifest listing segments in order; promotion to ghost band = transcode and copy to `~/.g3xn/tracks/<song-key>/track.m4a`.
- Song-change source: hook the stage's "current song changed" event with a short debounce (e.g. ignore a change back within 2 s); raw patch changes would split mid-song whenever a song uses several patches.
- Never stop the stream between songs or in the break: a stopped USB stream is an idle device for the USB power manager (Q5), and restarting a stream re-opens the device (new latency, possible failure).

### Gaps
- No primary source for MixPre pre-roll (10 s) or for Reaper/DAW "auto-split on marker" behaviour was fetched; the design above is standard practice but the DAW comparison is unsourced.

## Q5. Device selection across reboots, hot-plug/reconnect mid-show, detecting channels and rates, running 3+ hours (memory, clock drift, timestamping)

### Takeaway
Store the device as a WASAPI-qualified name query and resolve it to an index at start; PortAudio only re-enumerates devices on `_terminate()`/`_initialize()` (which closes every open stream, so the engine must own all streams), and hot-plug notifications can come from `pycaw.callbacks.MMNotificationClient` (Core Audio `IMMNotificationClient`); for a 3-hour show keep the stream running continuously, disable USB power management on the interface's root hub/host controller, and run a watchdog that compares delivered sample count with elapsed stream time, because WASAPI can drop samples without raising a flag.

### Cited Findings
- Name queries: `device` may be "a device index or a case-insensitive query string" — [sounddevice streams docs](https://python-sounddevice.readthedocs.io/en/0.5.6/api/streams.html); the implementation splits the query on whitespace and requires every substring in "name, host API" (installed sounddevice.py `_get_device_id`: `query_string.split()`). Verified on the dev PC: `sd.query_devices('Steam Streaming Microphone', kind='input')` → `ValueError: Multiple input devices found` (DirectSound, WASAPI, WDM-KS entries); `'Steam Streaming Microphone, Windows WASAPI'` → `No input device matching` (the comma sticks to a word); `'Steam Streaming Microphone WASAPI'` with `kind='input'` → index 21; without `kind` it is still ambiguous (an output entry matches too); a missing device gives `ValueError: No input device matching 'Scarlett 2i2 WASAPI'`.
- Device list refresh: PortAudio enumerates at `Pa_Initialize`; "The final matching call to Pa_Terminate() will automatically close any PortAudio streams that are still open", and failing to terminate "may result in serious resource leaks, such as audio devices not being available until the next reboot" — [PortAudio portaudio.h docs](https://www.portaudio.com/docs/v19-doxydocs/portaudio_8h.html). sounddevice exposes the private `_initialize()` ("automatically called with the import sounddevice statement") and `_terminate()` (installed sounddevice.py, lines 2918–2954; also listed in the API index of 0.5.x — [sounddevice genindex 0.5.3](https://python-sounddevice.readthedocs.io/en/0.5.3/genindex.html)). Verified on the dev PC only that the call sequence is safe: `sd._terminate(); sd._initialize()` ran without error and `query_devices()` returned the same 29 entries afterwards (nothing was plugged or unplugged, so actual re-enumeration of a new device was *not* demonstrated); calling `_terminate()` with a stream open raised nothing and the stale stream object could still be `stop()`ped/`close()`d afterwards. A Stack Overflow report says the same trick did not refresh on macOS/Homebrew — [kiwix mirror of SO 74273081](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/74273081/python-portaudio-can-t-update-audio-devices-mac) (unanswered).
- Event-driven hot-plug: `IMMNotificationClient` "provides notifications when an audio endpoint device is added or removed, when the state or properties of an endpoint device change, or when there is a change in the default role"; registered through `IMMDeviceEnumerator::RegisterEndpointNotificationCallback`; "The methods of the interface must be nonblocking" — [Microsoft Learn, IMMNotificationClient](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient). pycaw ships `MMNotificationClient(COMObject)` with `on_device_added`, `on_device_removed`, `on_device_state_changed`, `on_default_device_changed`, `on_property_value_changed`, registered with `AudioUtilities.GetDeviceEnumerator().RegisterEndpointNotificationCallback(monitor)` — [pycaw callbacks.py](https://raw.githubusercontent.com/AndreMiras/pycaw/master/pycaw/callbacks.py); "Pycaw currently supports Python 3.10 through 3.14 on Windows" — [pycaw README](https://github.com/AndreMiras/pycaw).
- Capability detection: `sd.query_devices(i)` gives `max_input_channels`, `default_samplerate`, `default_low/high_input_latency` per host-API entry (verified: the WASAPI entry reported 1 channel/44 100 Hz, the MME and WDM-KS entries 8 channels for the same virtual device); `sd.check_input_settings(device, samplerate, channels, dtype, extra_settings)` tests a configuration without opening it — [sounddevice platform-specific settings](https://python-sounddevice.readthedocs.io/en/0.5.6/api/platform-specific-settings.html) (verified results in Q1).
- Silent sample loss, verified on the dev PC (30 s each, delivered frames ÷ rate vs. wall time between first and last callback): MME 44.1 k 100.0 %; WASAPI shared at the native 44.1 k 100.0 %; WASAPI exclusive 48 k 100.0 %; WDM-KS 48 k 100.0 %; **WASAPI shared 48 k with `auto_convert=True` 97.4 %**, and 84.5 s of audio in 90.0 s (93.9 %) in the 90 s engine run — in every case with no `input_overflow`/`input_underflow` flag, although PortAudio defines `paInputOverflow` precisely as "data prior to the first sample of the input buffer was discarded" — [PortAudio portaudio.h docs](https://www.portaudio.com/docs/v19-doxydocs/portaudio_8h.html); the auto-convert path is Windows' own "system-level channel matrix mixer and sample rate converter" inserted by `paWinWasapiAutoConvert` — [pa_win_wasapi.h](https://github.com/PortAudio/portaudio/blob/master/include/pa_win_wasapi.h).
- USB power management: selective suspend "allows the hub driver to suspend an individual port"; "Selective suspend is enabled by default. Microsoft strongly recommends not disabling selective suspend" — [Microsoft Learn, USB Selective Suspend](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-selective-suspend). Audio vendors say the opposite for interfaces: MOTU: clear "Allow the computer to turn off this device to save power" on every USB Root Hub, set USB Selective Suspend to Disabled, clear "Allow applications to take exclusive control" on the device, turn off Fast Startup, buffer 256–512 samples, no unpowered hubs, cable ≤ 6 ft — [MOTU, Troubleshooting Windows audio](https://motu.com/techsupport/technotes/troubleshooting-windows-audio); Rational Acoustics (Smaart, a long-running measurement app): interfaces "disconnect or stop working after a period of inactivity" on Windows 11/10 due to USB power management; disable selective suspend globally, then in Device Manager (View → Devices by connection) uncheck power saving on the interface's parent USB Root Hub and host controller, restart; avoid USB extenders and multi-port hubs; bus-powered interfaces with phantom power can overload hubs — [Rational Acoustics KB](https://support.rationalacoustics.com/support/solutions/articles/150000091757--windows-audio-device-disconnects-or-stops-working-after-inactivity-within-smaart); Native Instruments and PreSonus add "Minimum processor state 99–100 %" and no sleep/disk timeouts — [NI Komplete Audio Windows issues](https://support.native-instruments.com/hc/en-us/articles/360017366438-Komplete-Audio-1-2-6-MK2-Audio-Issues-Windows), [PreSonus advanced power options](https://support.presonus.com/hc/en-us/articles/210046213-Windows-Vista-7-and-8-Advanced-Power-Options-Settings) (both from search snippets; pages not fetched).
- Clock accuracy: "Consumer/Standard: ±50 to ±100 PPM; Pro Audio Interfaces: ±10 to ±25 PPM; Master Clocks: <1 PPM", and 100 ppm "means two recordings diverge by about 360 ms per hour" — [ASIO4ALL, device aggregation](https://asio4all.org/device-aggregation/); word-clock error "can be up to 50 ppm even in good quality equipment" — [Digital Sound & Music, Word Clock](https://digitalsoundandmusic.com/?p=1284).
- Python's clock: on Windows, Python 3.13 "monotonic() now uses the QueryPerformanceCounter() clock for a resolution of 1 microsecond, instead of the GetTickCount64() clock which has a resolution of 15.6 milliseconds" (gh-88494); `time.time()` likewise moved to `GetSystemTimePreciseAsFileTime()` — [What's New in Python 3.13](https://docs.python.org/3/whatsnew/3.13.html). Verified on the dev PC (3.12.13): `time.get_clock_info('monotonic')` → `GetTickCount64()`, resolution 0.015625; `perf_counter` → `QueryPerformanceCounter()`, resolution 1e-7.

### Inferences
- Persist the device as `"<WASAPI name> WASAPI"` (space-separated, no comma) and resolve it with `sd.query_devices(q, kind='input')` at start; fall back to a fuzzy match on the WASAPI entries (`hostapi == index of 'Windows WASAPI'`) when the exact name changed (e.g. "2- Scarlett 2i2" after a port change) and surface the choice in the UI. Switch `voice.microphones()` from the MME host API to WASAPI so names are not truncated and timestamps exist.
- Hot-plug procedure: on `on_device_removed`/state change (pycaw) or on a watchdog trip (no callback for > 2 s, or a `PortAudioError` from `stream.active`): close *all* streams (engine + any voice stream), `sd._terminate(); sd._initialize()`, re-resolve the name, reopen, open a new file segment and mark the gap in the manifest; retry with back-off while the device is absent. Because `_terminate()` closes every stream, this only works if one component (the engine) owns every sounddevice stream in the process.
- Soak test to run on the real interface before trusting any host API (this is the rates.py core; it needs only sounddevice):
  ```python
  import time, sounddevice as sd
  dev = sd.query_devices('Scarlett WASAPI', kind='input')['index']      # space-separated substrings, no comma
  def soak(label, seconds=60, **kw):
      st = dict(n=0, frames=0, first=None, last=None, flags=set())
      def cb(data, frames, ti, status):
          st['n'] += 1; st['frames'] += frames
          if status: st['flags'].add(str(status))
          if st['first'] is None: st['first'] = time.perf_counter()
          st['last'] = (time.perf_counter(), frames)
      with sd.InputStream(callback=cb, dtype='float32', blocksize=0, **kw) as s:
          sr, lat = s.samplerate, s.latency; time.sleep(seconds)
      wall = st['last'][0] - st['first'] + st['last'][1] / sr; got = st['frames'] / sr
      print(f'{label}: delivered {got/wall*100:.1f}% of {wall:.1f}s, latency {lat*1000:.0f} ms, flags {st["flags"] or "none"}')
  mix = sd.query_devices(dev)['default_samplerate']
  soak('WASAPI shared @mix', device=dev, samplerate=mix, channels=2, extra_settings=sd.WasapiSettings())
  soak('WASAPI shared 48k auto_convert', device=dev, samplerate=48000, channels=2, extra_settings=sd.WasapiSettings(auto_convert=True))
  soak('WASAPI exclusive 48k', device=dev, samplerate=48000, channels=2, extra_settings=sd.WasapiSettings(exclusive=True))
  ```
  Expect 100 % for every mode you intend to use; anything below ~99.5 % with no flags is the silent-loss failure seen on the dev PC. Run it for an hour once to see drift and whether USB power management bites.
- Watchdog metrics per 10 s: callbacks received, `status.input_overflow` count, delivered frames ÷ rate vs `stream.time` delta (alarm if it diverges by more than ~0.5 %), `cpu_load`, queue depth; push them to the UI so a silent WASAPI stall or sample loss is visible on stage.
- 3-hour run: memory is bounded by the ring, the queue and streaming writes (no accumulation); clock drift between the interface (±25–100 ppm) and the laptop's QPC is up to 0.1–0.36 s per hour; the recording itself does not care (sample count is truth), but the beat tracker's wall-clock mapping must be re-estimated continuously (Q8) rather than fixed at start.
- Do the Windows power checklist once on the gig laptop: disable USB selective suspend, uncheck "allow the computer to turn off this device" on the interface's root hub and host controller, High-performance/plugged-in power plan, no sleep on lid close, Fast Startup off, and plug the interface directly into the laptop; Microsoft's "do not disable" advice is about battery life, which is irrelevant on stage.

### Gaps
- Whether the WASAPI auto-convert sample loss reproduces on a real UAC2 interface is unknown (virtual device only); the recommendation to avoid auto_convert stands regardless because matching the mix rate costs nothing.
- Whether a newly attached interface actually appears after `_terminate()/_initialize()` was not tested (no device to plug on the dev PC); only the absence of errors was verified. No GitHub issue in python-sounddevice about stale device lists was located (search found only the macOS Stack Overflow report); the `_terminate/_initialize` workaround is private API and undocumented.
- pycaw's `MMNotificationClient` requires COM threading setup (`sys.coinit_flags = 0` before importing pycaw/comtypes per its session-notification docstring); its interaction with uvicorn's threads and with pywebview in the same process was not tested.

## Q7. Recording in the browser (MediaRecorder from getUserMedia) vs in the daemon; the phone as a second source; level metering (dBFS/LUFS) for the "3 dB off the set" recap

### Takeaway
Record in the daemon: browser tabs are throttled to one timer per minute after 5 minutes hidden (a silent page), Chrome's MediaRecorder WebM output has no Cues and (when chunked) no Duration so `<audio>` cannot seek without a server-side remux, and the daemon already owns the interface; the phone's mic stays the second *voice* source it is today, not a recording source. Meter with per-block RMS/peak in dBFS for the live scope and with pyloudnorm (BS.1770-4, 0.2.0 Jan 2026) short-term/integrated LUFS per song for the recap.

### Cited Findings
- Chrome timer throttling: intensive throttling (timers checked "once per minute") applies when the page "has been hidden for more than 5 minutes", the timer chain count ≥ 5, "the page has been silent for at least 30 seconds" and WebRTC is not in use; playing sound "counts as activity" for 30 s after it stops but "A silent audio track does not count"; getUserMedia/MediaRecorder are not named as exemptions (only an `RTCPeerConnection` with a live `MediaStreamTrack` or open data channel) — [Chrome blog, Timer throttling in Chrome 88](https://developer.chrome.com/blog/timer-throttling-in-chrome-88). The project's own code already budgets for this: voice.py's `STAGE_HOLD` comment says "a hidden window's timers can be slowed to once a minute".
- MediaRecorder WebM: "Starting with Chrome 140, [non-chunked recordings] include the Duration element but no Cues"; chunked recordings (timeslice/`requestData()`) have "No Duration and no Cues"; without Cues "the player must read all data up to the target point" to seek and in Chrome "seeking and total length are only available after the whole file is downloaded and parsed"; fix by remuxing: `ffmpeg -i nocues.webm -c copy -cues_to_front 1 withcues.webm` — [addpipe blog, 2026-05-29](https://blog.addpipe.com/duration-in-webm-videos-produced-by-chrome/); client-side patching library — [fix-webm-duration](https://github.com/yusitnikov/fix-webm-duration); the Chromium bug is reported as WontFix in a Stack Overflow answer — [SO 50586612 (kiwix mirror)](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/50586612/seeking-is-not-working-in-recorded-video-with-mediarecorder-api).
- pyloudnorm 0.2.0 released 2026-01-04 ("Implementation of ITU-R BS.1770-4 loudness algorithm in Python"); `meter = pyln.Meter(rate); meter.integrated_loudness(data)` with `data` shaped (samples, channels); `meter.loudness_range(data)` (EBU Tech 3342); default gating block 400 ms (`block_size` configurable); needs SciPy/NumPy, Python ≥ 3.9; releases 2018, 2019, 2023, 2026 (infrequent, one maintainer) — [pyloudnorm on PyPI](https://pypi.org/project/pyloudnorm/).
- EBU R 128 definitions: momentary loudness = 400 ms sliding window, short-term = 3 s window, integrated = whole programme gated at −70 LUFS absolute and −10 LU relative; loudness range (LRA) describes "the loudness variation (dynamics) of a programme"; true peak ≤ −1 dBTP; target −23 LUFS ±0.5 LU (±1 LU for live); LUFS ≡ BS.1770 LKFS; EBU Tech 3341 defines "EBU Mode" metering — [Wikipedia, EBU R 128](https://en.wikipedia.org/wiki/EBU_R_128).
- The existing scope uses the browser's `getUserMedia` on a chosen device, and the phone joins over Tailscale HTTPS; the daemon already receives phone recordings for "Hey Claude" (task brief; voice.py `decode()` resamples uploaded audio with PyAV).

### Inferences
- There is no case for browser recording of the band mix: it would need the laptop's Chrome tab to stay visible for 3 hours, produce WebM/Opus (lossy, no seek metadata) that must be remuxed server-side anyway (and there is no ffmpeg CLI; PyAV could remux), and it could not time-stamp against the daemon's clock. The daemon's WAV path is lossless, seekable and timestamped.
- The browser scope can keep using `getUserMedia` on the same interface (shared WASAPI) — or, cheaper for the phone, subscribe to the daemon's meter stream over the existing WebSocket hub so the phone does not need its own capture at all.
- The phone mic is useful only as a voice source (already implemented) or, at most, as an ambience reference; its Opus/WebM uploads are fine for whisper but not for the ghost band.
- Metering plan: in the writer thread compute per 10 ms block `rms_dbfs = 20*log10(sqrt(mean(x**2)) + 1e-12)` and `peak_dbfs = 20*log10(max(abs(x)))` per channel with a 1–2 s peak hold for the scope; keep a 3 s short-term LUFS (pyloudnorm `Meter(rate)` on the native-rate ring, or a K-weighted RMS) for a live "level vs set" indicator; at song close compute integrated LUFS and LRA from the closed WAV (pyloudnorm on the whole file; 1 GB/h WAV is fine to read back once) and store them in the segment's JSON for the "songs 3 dB off the set" recap (compare each song's integrated LUFS with the set median). LUFS is the right unit because it is what "feels" 3 dB louder; peak dBFS only tells whether the interface clipped.

### Gaps
- Whether an active `getUserMedia` capture (without WebRTC) exempts a hidden Chrome tab from intensive throttling is not stated in Chrome's documentation; the MediaRecorder itself keeps running in the renderer, but the page's JavaScript upload loop would be throttled.
- iOS Safari's background-tab suspension (relevant to the phone) was not sourced.
- Real-time (streaming) LUFS with pyloudnorm per block was not benchmarked; its API is whole-array, so a 3 s rolling window would be recomputed per update (cheap at 48 kHz stereo, but unmeasured).

## Q8. Latency and clock: obtaining capture timestamps (stream.time, time_info, latency) so a beat detected at buffer time t maps to wall-clock

### Takeaway
On Windows, PortAudio's stream clock *is* `time.perf_counter()` (QueryPerformanceCounter seconds since boot; difference measured as 0.0000 s), so a WASAPI callback's `time_info.currentTime` minus `stream.latency` (22 ms here) is the wall-clock moment the first sample of that block entered the engine, and sample-count arithmetic from there gives every later sample; keep a running linear fit of (cumulative frames → currentTime) to absorb the ±100 ppm interface clock drift, treat `inputBufferAdcTime` as advisory (on this build it was 20–30 ms *after* `currentTime`, roughly `currentTime + latency`), use `perf_counter` (not `time.monotonic`, which is 15.6 ms-granular on Python 3.12) and calibrate the residual acoustic/USB offset once with a click.

### Cited Findings
- PortAudio: the callback's `timeInfo` values "are expressed in seconds and are synchronised with the time base used by Pa_GetStreamTime()", whose values "are monotonically increasing and have unspecified origin" and may be used "for synchronizing other events to the audio stream, for example synchronizing audio to MIDI" — [PortAudio portaudio.h docs](https://www.portaudio.com/docs/v19-doxydocs/portaudio_8h.html). sounddevice: `time.inputBufferAdcTime` is "the ADC capture time of the first sample in the input buffer", `time.currentTime` "the time the callback was invoked", `Stream.time` shares that clock, `Stream.latency` "provides the most accurate estimate of input/output latency available" and "can differ significantly from the value passed to the constructor" — [sounddevice streams docs](https://python-sounddevice.readthedocs.io/en/0.5.6/api/streams.html).
- Verified on the dev PC: `stream.time - time.perf_counter()` = −0.0000 s on four samples (same clock and epoch), while `stream.time - time.monotonic()` wandered +0.022…+0.036 s (GetTickCount64 granularity on Python 3.12); Python 3.13 moves `time.monotonic()` to QPC — [What's New in Python 3.13](https://docs.python.org/3/whatsnew/3.13.html).
- Verified on the dev PC, WASAPI exclusive 48 kHz: two consecutive callbacks had identical `currentTime` and `inputBufferAdcTime` values 10 ms apart that were 20–30 ms *later* than `currentTime` (`adc − current = +0.020` and `+0.030`, i.e. about the reported 20 ms latency plus one block); in shared mode `adc − current` varied between −0.007 and +0.011 across consecutive 480-frame callbacks. MME reports both fields as 0.0; WDM-KS reports `inputBufferAdcTime` relative to stream start. The documented meaning is "the ADC capture time of the first sample in the input buffer", which should precede the callback — [sounddevice streams docs](https://python-sounddevice.readthedocs.io/en/0.5.6/api/streams.html).
- Host buffering: Windows shared-mode capture runs on 10 ms engine periods by default; capture latency is "the delay between the time that a sound is captured from the microphone, until the time it's sent to the capture APIs" — [Microsoft Learn, Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio). Measured `stream.latency` on the dev PC: 0.022 s (WASAPI shared), 0.020 s (exclusive).
- Clock drift magnitudes (±10–100 ppm, up to 360 ms/h) — [ASIO4ALL, device aggregation](https://asio4all.org/device-aggregation/) (see Q5).

### Inferences
- Timestamping recipe: in the callback record `(frames_before_this_block, time_info.currentTime)`; the writer keeps a clock model `t_perf(sample_index) = a + b·sample_index` fitted by a slow recursive least squares / exponential average over the last few minutes of those pairs (b ≈ 1/rate, corrected by drift); a beat detected at absolute sample index k maps to `t_perf(k) − stream.latency − cal_offset`, then to UTC with a one-time `time.time() − time.perf_counter()` offset (refreshed occasionally; 3.13's `time.time()` is also microsecond-precise). Expected accuracy: a few ms, limited by the 10 ms period jitter in `currentTime`.
- Give analysis consumers absolute sample indices (frames counted since stream start) rather than times; the ring buffer stores the index of its newest sample so the beat tracker can ask "samples i..j" and compute times through the clock model. This also makes the per-song JSON (first sample index + its time) sufficient to align recordings with the stage's song clock afterwards.
- `cal_offset` (interface ADC → USB → engine → callback beyond what `stream.latency` reports, plus mixer/aux delay) can be measured once per interface by playing a click from the daemon and detecting it in the capture; it is constant for a given setup and only matters at the ±10 ms level.
- Do not use `inputBufferAdcTime` directly on this PortAudio build: its sign relative to `currentTime` contradicts the API description (later, not earlier), so a +40 ms error would follow; `currentTime − latency` is consistent with the documented meaning of `Stream.latency`.

### Gaps
- The PortAudio WASAPI source line computing `inputBufferAdcTime` was not fetched, so the "currentTime + latency" behaviour is an observation on one build, not a documented fact.
- Whether `stream.latency` on a real UAC2 interface includes the driver's USB buffering (likely larger than the 20–22 ms seen on the virtual device) is unmeasured; the click calibration resolves it in practice.
