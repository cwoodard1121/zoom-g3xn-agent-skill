## KQ1. G3n/G3Xn MIDI implementation for tempo: MIDI Clock, CC tap tempo, which parameters follow tempo, range, per-patch vs global, echoes, Rhythm/Looper over MIDI

### Takeaway
Zoom documents a single 40–250 bpm tempo "used by every effect, rhythms and the looper", set by tap/knob, with no MIDI implementation at all beyond "USB MIDI" in the spec table; everything the daemon already does (set tempo with SysEx `0a 02`, hear the tap echo) is reverse-engineered, and nothing documented or reported suggests the G3Xn accepts MIDI Clock (0xF8) or a tap-tempo CC. There is no evidence of per-patch tempo storage (Zoom documents one shared setting; none of the user's 150 patch images holds a tempo), so treat it as device-global in fw 2.20, pending hardware test 7(b) in KQ7.

### Cited Findings

(manual p.35, "Adjusting the rhythm tempo") — [Zoom G3n/G3Xn manual](https://zoomcorp.com/media/documents/E_G3n_G3Xn.pdf); same text on [manualslib p.35](https://www.manualslib.com/manual/1239427/Zoom-G3xn.html?page=35)

- **[RE]** Rhythm and Looper are chain effects: zoom-zt2 issue #34 ("16, 240 == Rhythm", "bpm 40 - 250", looper "Stop: stop, finish, fade out", "one can turn these FX on/off in slot", "P7 modifies the stop"); the repo's catalog lists them as built-ins `0x1e000010` Rhythm (Pattern, Dummy, BPM, VOL) and `0x1f0000x0` LP Mono/Stereo/Mono 2/Stereo 2 (Time, Undo, Stop, VOL) — [zoom-zt2 #34](https://github.com/mungewell/zoom-zt2/issues/34), [tools/build_catalog.py](https://github.com/cwoodard1121/zoom-g3xn-agent-skill/blob/main/tools/build_catalog.py)
- **[RE]** Patch format: zoom-zt2's `PPRM_rev` for the 12-byte PPRM chunk (G1Four/G3n family) decodes only `patchVolume` (7 bits) and `editSlot` (3 bits), no tempo; its 32-byte `PPRM_v2_rev` for the MS-plus pedals *does* contain an 8-bit `tempo` plus `bpmSlot`/`rhythmSlot`/`looperSlot` bitfields — [zoom-zt2 decode_preset.py](https://github.com/mungewell/zoom-zt2/blob/HEAD/decode_preset.py); zoom-explorer (MS-plus) likewise stores a per-patch `tempo` from PRM2 — [thammer/zoom-explorer ZoomPatch.ts](https://github.com/thammer/zoom-explorer/blob/HEAD/src/ZoomPatch.ts)
- **[empirical]** Scan of the user's 150-slot backup (`data/pedal_dump/*.zptc`, all 736-byte PTCF images, PPRM 12 bytes in every one): the bits that vary across patches outside the known volume/slot field (bits 63–72) are small bitfields (27–33, 45, 49–51, 59–60, 74–76, 78–80, 82–84); no 8-bit window ever holds BPM-like values (the only window whose values all fall in 40–250 is the arithmetic set {66, 100, 134, 168, 202}, i.e. two flag bits); the PTCF header varies only in length (bytes 4–5) and effect count (byte 12); the user's own patches share the same PPRM value families as factory demos — scan script kept at `M:\temp\claude\C--Users-camer-Desktop-aiprojects-zoom\7b6bbdc0-17e0-43ff-adc9-29171d4dfeaa\scratchpad\scripts\pprm_scan2.py` (format notes: [g3xn/patch.py](https://github.com/cwoodard1121/zoom-g3xn-agent-skill/blob/main/g3xn/patch.py))

### Inferences
- MIDI Clock reception is undocumented, unreported and, given that the pedal's USB-MIDI exists as Guitar Lab's transport (SysEx plus PC/CC bank), unlikely; but it is a 10-minute test, see Gaps. Tap tempo via CC: no evidence at all; the only tap path is the footswitch (or the `0a 02` SysEx, which is equivalent to "set the number").
- Tempo behaves as a device-global setting in fw 2.20: the manual describes one setting shared by everything, sibling manuals call it the "master tempo" (KQ3), the SysEx lives under "system setting" `0a`, and the 736-byte patch image has nowhere to store it (empirical scan; a per-slot table elsewhere in flash is not ruled out by the scan, only by test 7(b)). Practical consequence: `Pedal.set_tempo` has no reason to be confined to the scratch slot (today `_live()` refuses edits unless the scratch slot is selected); allowing it on any slot is a one-flag change, to be verified on hardware (does the tempo survive a patch change? does the `0a 02` echo arrive with byte 5 = 0 as the tap does?). The per-song tempo the app stores in gigs therefore has to be pushed on every song change.
- "Can MIDI start the Rhythm/Looper": the Rhythm is a chain effect whose on/off is the footswitch, and `Pedal.stomp()` already toggles effects "the way the pedal's own footswitches do", so turning the Rhythm slot on by SysEx plausibly starts it; the looper's record/play/overdub/stop are multi-press footswitch gestures and its "Stop" knob is a mode (stop/finish/fade), not a trigger, so looper transport over MIDI is doubtful. Untested.
- Safety: because changing the tempo erases a playing loop (manual p.37) and older Zooms dropped delay buffers on tempo changes (user report), the app should push tempo only on settled changes, never per beat, and never while the looper is in use.

### Gaps
- Whether the G3Xn reacts to 0xF8 clock is untested. Test (with ToneLib closed, daemon connected): `mido` → send `start`, then `clock` at 24 ppqn for 4 s at an unusual BPM (e.g. 97), then `stop`; watch `Pedal.events()` for an `0a 02` message and read the Rhythm BPM / TAP TEMPO screen. No `0a 02` and no screen change = no clock support.
- Whether the tempo persists across patch changes and power cycles is undocumented (test: set 97 by SysEx, change patch, open TAP TEMPO).
- No Zoom firmware release notes exist on the support page, so "fw 2.x changes to tempo" cannot be sourced.
- Whether SysEx on/off of the Rhythm slot starts playback, and what the Rhythm's "BPM" knob is (the same global tempo or a separate value) — untested; the catalog's built-in knob ranges (max 127) are placeholders from the pedal's screen names, not from a .ZD2.

## KQ2. Zoom's own apps (Guitar Lab / Handy Guitar Lab) and the pedal's own tempo UI; global vs per-patch in fw 2.x

### Takeaway
Guitar Lab exposes the tempo as a TAP button plus an editable number next to the patch level; the pedal shows the tempo on its TAP TEMPO screen; neither Zoom document says "per patch", and the empirical scan shows it is not stored in patches.

### Cited Findings
- **[Zoom-doc]** Guitar Lab Reference Guide v7.0 p.27, section "Save a patch / Adjust patch level / Adjust tempo / Tune your instrument": "Adjust tempo — 1. Click the 'TAP' button repeatedly to set the tempo to your mouse click interval. 2. Double-click the tempo value. 3. Type in the desired tempo value. 4. Press ENTER to accept the change. Press ESC key to cancel the change." — [Guitar Lab guide](https://zoomcorp.com/documents/1956/E_GuitarLab_v7.0.pdf)
- **[Zoom-doc]** The support page lists Guitar Lab 7.3 as current while the published reference guide is v7.0 — [Zoom support page](https://zoomcorp.com/en/us/multi-effects/guitar-effects/g3n-g3xn/g3ng3xn-support/)
- **[Zoom-doc]** On the pedal, the tempo is set/read on the TAP TEMPO screen (press-and-hold a footswitch in STOMP or MEMORY mode), tapped at least twice or turned with the centre unit's knob (manual p.44–45); the rhythm screen's tempo knob shows 40–250 bpm (p.35) — [manual](https://zoomcorp.com/media/documents/E_G3n_G3Xn.pdf)
- **[Zoom-doc, sibling]** G1 Four manual p.27 "Adjusting the master tempo": the master tempo is "the tempo shared by effects, rhythms and the looper", set from SETTING → SETUP, "This can be set from 40 to 250." — [manualslib G1 Four p.27](https://www.manualslib.com/manual/1522270/Zoom-G1-Four.html?page=27)
- **[Zoom-doc, sibling]** G11 manual p.39 "Adjusting the master tempo": "The tempo used by rhythms, the looper, delay effects and some modulation effects can be adjusted." "The tempo can be set from 40 to 250 ♩ per minute."; p.15 lists "Set the tempo used for the effects, rhythms and looper" among global Home-screen functions — [G11 manual](https://zoomcorp.com/media/documents/E_G11v2.pdf)
- **[empirical]** No tempo field in any of the 150 backed-up G3Xn patch images (see KQ1).

### Inferences
- Guitar Lab's tempo control sits in the patch-editing toolbar because that is where editing happens, not because the value is saved per patch; across the G1 Four/G3n/G5n/G11 generation Zoom's wording is consistently one shared ("master") tempo. Treat it as global; if a gig needs per-song tempos, the app has to push them.
- Handy Guitar Lab (the iOS/Android app) was not researched and is listed as a gap; the G3n is served by desktop Guitar Lab.

### Gaps
- Whether Handy Guitar Lab lists the G3n/G3Xn at all, and what it shows for tempo — not researched.
- Whether the G3Xn's TAP TEMPO screen shows the value received over SysEx immediately (expected, untested).

## KQ3. Related Zoom pedals (G11, G1 Four, G5n, B3n, MS-50G+): do any accept MIDI Clock? (triangulation only)

### Takeaway
Only the G11 (2020, with 5-pin MIDI IN/OUT) documents MIDI Clock in and out; the USB-only "n"/"Four"/MS-plus pedals document nothing of the kind, which makes clock support on the G3Xn improbable, though not disproven.

### Cited Findings
- **[Zoom-doc]** G11 manual p.84: "RECEIVE MIDI CLOCK ... ON: Data is received. (The G11 will synchronize to the tempo of the external device.)" and "SEND MIDI CLOCK ... ON: Data is transmitted. (An external device can be synchronized to the G11 tempo.)"; p.80: "The tempo used by the MIDI device can be used to synchronize the delay and modulation effects of the G11." — [G11 manual](https://zoomcorp.com/media/documents/E_G11v2.pdf)
- **[Zoom-doc]** G11 MIDI implementation chart (p.105, dated March 16, 2020; verified on the rendered page, not just the text layer): System Real-time Clock transmitted **o** / recognized **o**; Command (start/stop) **x/x**; Song Position, Song Select, Tune **x/x**; Control Change transmitted o* / recognized x; Program Change o/o; System Exclusive **x/x**; Note, Velocity, Aftertouch, Pitch Bend all x — [G11 manual](https://zoomcorp.com/media/documents/E_G11v2.pdf)
- **[Zoom-doc]** G11 tap tempo: "Press and hold the BANK ▲ switch to enable tap tempo input." (p.12) — [G11 manual](https://zoomcorp.com/media/documents/E_G11v2.pdf)
- **[Zoom-doc]** G5n manual p.46 "Setting the tempo": tempo is used for the looper, rhythm and delay, "some modulation effects can be synchronized", set by choosing an effect that supports sync and setting "Time" or "Rate" to a note value; no MIDI mention — [manualslib G5n p.46](https://www.manualslib.com/manual/1067959/Zoom-G5n.html?page=46)
- **[Zoom-doc]** G1 Four: global master tempo 40–250, no MIDI mention — [manualslib G1 Four p.27](https://www.manualslib.com/manual/1522270/Zoom-G1-Four.html?page=27)
- **[RE]** zoom-zt2 supports G1Four (tested), expects G1XFour/B1Four/B1XFour/G3n/G3Xn/B3n/G5n to work, and the MS-50G+/60B+/70CDR+/80IR+ partially; all over USB-MIDI SysEx; no clock handling anywhere — [mungewell/zoom-zt2](https://github.com/mungewell/zoom-zt2)
- **[RE]** MS-plus pedals expose tempo as a patch/system parameter over SysEx (issue #86 "Changing Tempo ... 02 = Tempo") and store tempo per patch in PRM2 — [zoom-zt2 #86](https://github.com/mungewell/zoom-zt2/issues/86), [zoom-explorer](https://github.com/thammer/zoom-explorer/blob/HEAD/src/ZoomPatch.ts)
- **[Zoom-doc]** The G3n/G3Xn have USB MIDI over Micro-B and no DIN jacks (manual specifications, p.51) — [manual](https://zoomcorp.com/media/documents/E_G3n_G3Xn.pdf)

### Inferences
- Zoom implemented clock sync exactly where it added DIN MIDI hardware and published a chart (G11). The G3n generation's USB-MIDI stack predates that and its SysEx protocol is what the G11 chart marks as "x" — so the two firmware families are not the same code path; nothing in the G11 chart transfers to the G3Xn.
- Even the G11 does not recognise Start/Stop or Song Position, so Zoom's clock sync (where it exists) is tempo-only: the tempo number follows the clock, nothing is phase-locked to the downbeat.

### Gaps
- No G5n/G3n firmware release notes were found to check whether 2.x changed MIDI behaviour.

## KQ4. Delay time to tempo: Time parameter ranges/units, tempo-synced note modes, what the catalog and Zoom's effect list say

### Takeaway
Every delay except Pitch DLY (and SlwAtkDly/SoftEcho, not in the 2017 list) carries Zoom's "tempo synchronization possible" icon on Time, as do Tremolo/Phaser/VinFLNGR/Vibrato/Slicer/WarpPhase rates, AutoPan Rate, LoopRoll Time and PhaseDly RATE; the pedal's own parameter records show those knobs have extra raw positions above the printed ms/rate range (23 for 4000 ms delays, 15 for 2000 ms delays, 28 for modulation rates, 10 for Tremolo, 1 "Sync" for SlapBackD, 0 for every non-icon knob) — these are the note-value positions, so the app can park Time on a note value and only push the BPM.

- **[Zoom-doc]** The Effects List's "Additional tables" (p.26) contain only the HPS scale table and the PDL Pitch colour table; there is no table naming the note values — [Effects List](https://zoomcorp.com/documents/68/E_G5n_G3n_G3Xn_FX-list.pdf.pdf)

### Inferences
- The surplus raw positions are the note values the manual refers to ("set that parameter ... to a note value (♪ or ♩)"). Working model (to verify by reading the screen): raw 0..(max−surplus) is milliseconds (shown value = raw + offset), and the top `surplus` positions are note values in ascending length, ending at "♩ x 8" for Dual DLY as printed. Which glyph each position is (eighth triplet, eighth, dotted eighth, quarter, …) is not in any document; `Pedal.screen()` on the scratch slot with Time set to each surplus raw value decodes them in one pass, and the result belongs in the catalog as per-effect "note positions".
- For every ♪ effect the app does not need to compute milliseconds at all: set Time/Rate to the wanted note position once (it is a normal knob write: slot, param, raw value) and push BPM with `Pedal.set_tempo`; the pedal recalculates. Compute ms only for non-♪ parameters: `ms = 60000 / BPM × beats` (quarter = 1, dotted eighth = 0.75, eighth = 0.5, triplet eighth = 1/3), `raw = round(ms) − display.offset`, clamped to the printed range (e.g. 120 BPM dotted eighth = 375 ms → Delay raw 374).
- A-Pan DLY "Cycle 1/4 – 50" with no icon and two below-zero raw positions is probably a fraction-of-beat setting that is not tempo-synced; leave it alone.

### Gaps
- The exact glyph sequence of the note positions (which raw value is ♩, ♪., etc.) and the clamp behaviour when a note value exceeds the delay's maximum (e.g. ♩ x 8 at 40 BPM = 12 s on a 4000 ms delay) are undocumented; both are screen-readable on hardware.
- Whether tempo-synced delays re-time smoothly or glitch (buffer drop) on a tempo change is unknown for the G3Xn (older Zooms reportedly dropped the buffer); matters for "live" tempo following.

## KQ5. Distributing a tempo/beat clock from a Python app on Windows: (a) MIDI Clock out, (b) Ableton Link, (c) a click for the drummer

### Takeaway
Link is the practical way to share tempo *and* beat phase with phones, DAWs and Link hardware, and two current Windows wheels exist for Python 3.12–3.14 (aalink 0.2.3, LinkPython-extern 1.3.0) plus a binding-free daemon (Carabiner); MIDI Clock out from Python over WinMM will have DAW-class millisecond jitter that measured studies call audible, so it is a best-effort extra, not the backbone. Link does not cross Tailscale/VPNs and often not venue Wi-Fi, so plan on a dedicated router or hotspot.

### Inferences
- MIDI Clock out from Python: a dedicated thread scheduling ticks against `perf_counter()` (sleep until ~1 ms before, then spin), `timeBeginPeriod(1)` via ctypes, above-normal process priority and a foreground (not minimised) window will produce clock of roughly DAW quality — i.e. millisecond-scale jitter that Helix/QC/BeatBuddy PLLs smooth into a usable *tempo* but not a studio-tight *phase*. Dedicated hardware (a Link→MIDI phone bridge into a cheap USB-MIDI interface, or a clock box) is the upgrade path if anyone complains. The µs-accurate timestamped scheduling in Windows MIDI Services is only reachable through the new SDK, not through python-rtmidi's WinMM path.
- On this PC (Windows 11 build 26200 = 25H2) Windows MIDI Services is already in-box and WinMM is redirected to it with multi-client access, so the memory note that ToneLib holds the "ZOOM G Series" port exclusively may be obsolete — worth a quick re-test, because it also decides whether a second MIDI app can share the pedal.
- Python version: stay on CPython 3.12 for binary wheels of python-rtmidi 1.5.8; on 3.13/3.14 either build from the python-rtmidi master (needs MSVC), use the PR artifacts, or switch mido's backend; aalink and LinkPython-extern both already ship 3.12–3.14 Windows wheels.
- Link licensing: aalink is GPLv3 and Link itself GPLv2+/proprietary; LinkPython-extern is Unlicense but still embeds Link (GPLv2+). For a private gig tool this is irrelevant; for distribution, Carabiner (separate process) avoids linking GPL code into the app.
- Venue networking: carry a travel router (or run the phone hotspot/laptop hotspot) and put the laptop and the drummer's phone on it; Tailscale stays for the remote-control https path but cannot carry Link.
- Drummer's click: the lowest-risk path is an audio click from the laptop into the drummer's IEM/headphone amp (no network, fixed latency); Link to a phone metronome is the "no cables" path and works because Link metronomes align downbeats to the shared beat (OnSong, Planning Center, Soundbrenner).

### Gaps
- No measured jitter figures for mido/python-rtmidi on Windows were found; the DAW figures (E-RM) are the best proxy. A 100-line test (send clock for 60 s, capture on a loopback or second interface, histogram the intervals) would settle it for this laptop.
- No Ableton statement on Link over phone hotspots was found (the help pages refused fetch); user reports suggest hotspots work since they are ordinary APs with multicast, but this is unverified.
- No authoritative "acceptable latency for a drummer's click" figure was found beyond the jitter-vs-latency statements above.
- The Midronome numbers are a vendor claim from a search snippet; the page now redirects.

## KQ6. Reverse direction: can the app listen to the drummer's click (Link or MIDI Clock) as the authoritative tempo, and which common click sources send it?

### Takeaway
Yes, and it is far cheaper and more exact than audio beat tracking: MIDI Clock receive needs only mido (24 ticks per beat, Start/Continue for phase), and Link receive is a property/callback in aalink; BeatBuddy, Helix (2.20+), Quad Cortex (CorOS 2.3.0+), DAWs and OnSong send MIDI clock, while OnSong, Planning Center, Soundbrenner's app and most phone metronomes speak Link.

### Cited Findings
- MIDI Clock tick rate is 24 per beat (so BPM = 60 / (24 × mean tick interval)) — [E-RM report](https://www.e-rm.de/data/E-RM_report_Jitter_02_14_EN.pdf); mido parses `clock`, `start`, `continue`, `stop`, `songpos` — [mido docs](https://mido.readthedocs.io/en/latest/message_types.html)
- aalink exposes `tempo`, `beat`, `phase`, `playing`, `num_peers` and `set_tempo_callback` / `set_start_stop_callback` / `set_num_peers_callback` — [aalink.cpp](https://github.com/artfwo/aalink/blob/HEAD/src/aalink.cpp)
- BeatBuddy sends clock Always On / While Playing and a Start at the intro or main beat (fw 1.85+); users report its clock is good as a master — [Singular Sound forum](https://forum.singularsound.com/t/beatbuddy-firmware-update-control-how-drunk-your-beatbuddy-gets-and-more-version-1-85/3267), [forum: as MIDI slave](https://forum.singularsound.com/t/beatbuddy-as-midi-slave-reliable/1639)
- Helix sends MIDI clock (5-pin and USB) since 2.20; Quad Cortex sends since CorOS 2.3.0 (USB, DIN, both) — [Line 6 thread](https://line6.com/support/topic/59573-helix-as-midi-clock-source), [Neural DSP 2.3.0](https://neuraldsp.com/quad-cortex-updates/cortex-control-public-release-and-coros-2-3-0-are-now-available)
- Ableton Live sends MIDI clock (and with Tempo Follower still sends it); Reason sends clock while Link-synced; Live's Tempo Follower itself "analyzes an incoming audio signal in real-time and interprets its tempo" and is "optimized for use with audio signals that have a clear rhythm" — [Ableton Live 12 manual](https://www.ableton.com/en/live-manual/12/synchronizing-with-link-tempo-follower-and-midi/), [Reason docs](https://docs.propellerheads.se/reason12/SynchronizationAndAdvancedMIDI.24.3.html)
- OnSong pushes song tempos into a Link session (Both/Lead) and receives MIDI Clock; Planning Center and Soundbrenner's app are Link peers — [OnSong Ableton Link](https://www.onsongapp.com/docs/features/ableton-link), [OnSong beat sync](https://onsongapp.com/docs/features/beatsync), [Planning Center](https://help.planningcenter.com/en/sync-the-metronome.html), [Soundbrenner listing](https://apps.apple.com/us/app/-/id1048954353)
- A phone can turn a Link session into hardware MIDI clock (Link to MIDI, iOS; Link to MIDI Bridge, Android), and AudioBus 3 is reported to relay Link ↔ MIDI clock reliably — [alexandernaut.com](https://alexandernaut.com/linktomidi/), [Beepstreet forum report](https://forum.beepstreet.com/discussion/comment/50146)
- Caveats from receivers: Helix reverts to the preset tempo when clock stops; an HX Stomp needed a Start before honouring clock — [Line 6 forum](https://line6.com/support/topic/70308-when-helix-receives-midi-clock-tempo-changes-cause-delay-pitch-morphing-even-with-tap-tempo-pitch-set-to-transparent), [Line 6 forum](https://line6.com/support/topic/68581-midi-clock-receive-stops/)

### Inferences
- A clock listener should (1) average tick intervals over ~1 beat (24 ticks) with outlier rejection, since DAW/USB clock jitters by several ms per tick (E-RM), (2) take beat 1 from Start/Continue + Song Position when present and otherwise count ticks modulo 24, (3) report "no clock" after ~0.5 s of silence rather than freezing the last tempo, and (4) feed the same "band clock" object as Link and audio detection.
- Which source wins should be explicit: Link if any peer is present, else MIDI clock if ticks are arriving, else audio detection, else the song's stored tempo — with a UI indicator of the active source, because Helix-style silent reverts are the usual live failure.

### Gaps
- Whether Soundbrenner's app or Pulse can *send* MIDI clock (as opposed to Link) was not confirmed; whether OnSong *sends* MIDI clock (it has a MIDI Clock settings page) was not confirmed.
- No Android metronome other than Soundbrenner's and Planning Center's was confirmed to support Link.

## KQ7. Practical recommendation: what the Python daemon should implement first for "band sync"

### Takeaway
Build one "band clock" (tempo, beat phase, source, confidence) fed by Link → MIDI clock in → audio detection → song default, push settled tempos to the pedal with the existing `set_tempo`, park synced effects on note positions, make the laptop a Link peer so phones follow it, and treat MIDI clock *out* as a last, best-effort extra.

### Cited Findings
- The pieces already exist in the daemon: `Pedal.set_tempo` (SysEx `0a 02`), the tap-tempo event (`{"type": "tempo"}`), `Pedal.screen()` for reading knob text, `stomp()` for footswitch-style on/off, and a per-song tempo in gigs — [pedal.py](https://github.com/cwoodard1121/zoom-g3xn-agent-skill/blob/main/g3xn/pedal.py), [daemon.py](https://github.com/cwoodard1121/zoom-g3xn-agent-skill/blob/main/g3xn/daemon.py), [APP_PLAN.md](https://github.com/cwoodard1121/zoom-g3xn-agent-skill/blob/main/docs/APP_PLAN.md)
- The pedal's tempo is a 40–250 global setting, synced parameters are the ♪ knobs, and tempo changes erase a playing loop — see KQ1/KQ4 citations ([manual](https://zoomcorp.com/media/documents/E_G3n_G3Xn.pdf), [Effects List](https://zoomcorp.com/documents/68/E_G5n_G3n_G3Xn_FX-list.pdf.pdf))
- Link bindings with current Windows wheels: aalink 0.2.3, LinkPython-extern 1.3.0; binding-free: Carabiner 1.2.0 — [PyPI aalink](https://pypi.org/project/aalink/), [PyPI LinkPython-extern](https://pypi.org/project/LinkPython-extern/), [Carabiner](https://github.com/Deep-Symmetry/carabiner)
- Computer-generated MIDI clock measured at ms-scale jitter that "would most probably fail a listening test" — [E-RM report](https://www.e-rm.de/data/E-RM_report_Jitter_02_14_EN.pdf)

### Inferences (the recommended order)
1. **Band clock abstraction** in the daemon: `{bpm, beat, phase, source: link|midi_clock|audio|song, updated_at}`; priority Link > MIDI clock > audio > song tempo; emit it to the stage view like the existing `tempo` event.
2. **Link peer first** (aalink, asyncio fits the daemon; `tempo` callback for receive, `link.tempo = x` to lead, `start_stop_sync_enabled`): one dependency, no hardware, and it covers the drummer's phone (Soundbrenner/Planning Center/OnSong), any laptop DAW and Link hardware. Document "same Wi-Fi, bring a travel router; not over Tailscale/VPN".
3. **MIDI clock listener** (mido, any USB-MIDI interface): covers BeatBuddy, Helix, Quad Cortex and DAWs that only speak clock; ~50 lines.
4. **Pedal push with hysteresis**: push `set_tempo` only when the band clock's rounded BPM changes by ≥1 and has been stable for ~1–2 s; never while the looper is recording/playing; never per beat. Allow `set_tempo` off the scratch slot once the hardware test confirms the tempo is global (one flag in `_live`, no protocol rewrite).
5. **Note positions, not milliseconds** for ♪ effects: read the surplus raw values on the scratch slot with `Pedal.screen()`, store them per effect in the catalog (e.g. `"note_positions": {"♪": 4001, "♪.": ..., "♩": ...}`), and let the gig editor pick "dotted eighth" for a song; compute ms (`60000/BPM × beats − offset`) only for non-♪ knobs and for pedals/effects without sync.
6. **MIDI clock out last**, as an opt-in "lead the band's clock" feature on a dedicated thread with `perf_counter` scheduling; label it as computer-grade clock, and point to a Link→MIDI phone bridge or clock box for players who need tighter phase.
7. **Ten-minute hardware tests to run before coding** (all on the scratch slot, ToneLib closed): (a) 0xF8 clock at 97 BPM — does `0a 02` echo or the TAP screen change? (b) set 97 by SysEx, change patch, re-open TAP TEMPO — still 97? (c) sweep Delay Time raw 4000..4022 and read the screen glyphs; (d) turn the Rhythm slot on by SysEx — does it play? (e) set ♩ x 8 at 40 BPM — what does the pedal do?

### Gaps
- Audio beat tracking is researched separately; its integration point is only the band clock's `audio` source.
- Nothing here was run against the pedal; items 7(a)–(e) are the open empirical questions.
