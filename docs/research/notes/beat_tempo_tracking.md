# Real-time (online, causal) beat, downbeat and tempo tracking from a live band's audio — Python on Windows, for g3xn

Research date: 2026-11-01. Scope: candidate algorithms and Python libraries for an ONLINE tracker that can start and hold the g3xn "song clock" (bars, beats, tempo) from the band mix or the guitar feed, with a confidence that lets the app fall back to the pedal's tap-tempo footswitch. Install feasibility was verified first-hand on the developer's Windows 11 laptop (CPython 3.12.10 system install plus uv-managed 3.12.13 and 3.13) — see the embedded logs. Offline tools (Beat This!, librosa, TempoCNN, essentia) are covered only to rule them out or to pre-process the stored reference recording.

Vocabulary used below: "online/causal" = emits a beat using only past audio; "latency" = how far behind the audio a beat is reported (the BeatNet+ paper defines it as the STFT hop size); F1 = beat/downbeat F-measure at the standard ±70 ms tolerance.

---

## Q1. Which libraries do ONLINE/causal beat tracking, and what is their 2026 Windows / Python 3.12–3.13 install status?

### Takeaway
Only four codebases actually implement causal tracking: madmom (`DBNBeatTrackingProcessor(online=True)` — beats only, no online downbeats), BeatNet / BeatNet+ (joint beat+downbeat+meter with particle filtering, PyTorch + madmom), BEAST (streaming Transformer, research code only), and the classic onset-plus-comb-filter trackers aubio and BTrack (beats + tempo only). On Windows with Python 3.12/3.13 the only one that installs with `pip` and no compiler is the maintained aubio fork `aubio-ledfx` (binary wheels cp311–cp315, verified here); madmom (and therefore BeatNet) must be compiled from the git main branch with MSVC Build Tools because the 2018 PyPI release is broken on NumPy ≥1.24 and no wheels or maintained drop-in fork exist; BTrack's PyPI package ships macOS-arm64 wheels only; essentia has no Windows wheel at all.

### Cited Findings

**madmom (CPJKU) — online DBN beat tracking, offline downbeats**
- The latest PyPI release is 0.16.1, shown as "Released: Nov 14, 2018" (the bundled release notes say 2017-11-14 — the two dates conflict); only a source tarball is published, no wheels for any platform; classifiers list Python 2.7, 3.5, 3.6, 3.7; licence "BSD, CC BY-NC-SA" (source BSD, models CC BY-NC-SA 4.0 — commercial use of the model files requires contacting Gerhard Widmer) — [madmom on PyPI](https://pypi.org/project/madmom/)
- 0.16.1 fails to import on modern NumPy with `AttributeError: module 'numpy' has no attribute 'float'` (issue opened Aug 24 2023, still open); maintainer superbock replied Aug 26 2023 that "there are many of these problems", the CI pipeline isn't fixed, and invited a PR; the most-upvoted workaround (Jan 17 2024) is `pip install git+https://github.com/CPJKU/madmom.git` because the bug is absent on the main branch; PR #542 (Dec 10 2024) replaces the aliases — [madmom issue #527](https://github.com/CPJKU/madmom/issues/527)
- A Feb 18 2026 issue reports the `np.float`/`np.int` aliases in 11 files of 0.16.1, gives a recipe (`Cython==3.0.10`, `setuptools`, `numpy==1.26.4`, then `pip install --no-build-isolation madmom==0.16.1`, then a post-install regex patch script) and asks for a 0.16.2/0.17 release; no maintainer response is visible — [madmom issue #557](https://github.com/CPJKU/madmom/issues/557)
- Building from GitHub with Cython 3.1.0 fails with `madmom/features/beats_crf.pyx:26:0: 'numpy/math.pxd' not found` (issue opened May 17 2025, open); a Windows user ("memecode", May 18 2025) got it built by applying PR #548; others fixed it with `cython==3.0.1`; on Jan 9 2026 a user installs from the `v0.17_fixes` branch; on Mar 3 2026 a commenter calls the project unmaintained and the "fixes" branches incomplete — [madmom issue #550](https://github.com/CPJKU/madmom/issues/550)
- PR #548 ("replace deprecated numpy.math use with libc.math", opened May 12 2025) is still open; its author notes the breakage came from files missing in Cython 3.1 wheels, "fixed in 3.1.2 afaik"; a fork `karimkfoure/madmom-plus` cites the PR on Oct 29 2026 — [madmom PR #548](https://github.com/CPJKU/madmom/pull/548)
- Other open issues: "Can we get a new release?" (#553, Jun 24 2025), "Installation fails" (#550), "Cant import madmom" (#547, May 2025), `cannot import name 'MutableSequence' from 'collections'` (#535, Jan 2024, a Python ≥3.10 break in 0.16.1), `longintrepr.h: No such file` (#521, May 2023, a Cython-vs-new-CPython build break) — [madmom issues list](https://github.com/CPJKU/madmom/issues?q=is%3Aissue+numpy+2)
- A Windows user (Mar 16 2024) reports that pulling madmom from GitHub and installing locally gives "version 0.17" which "does not have the numpy issue" and "seems to work okay on windows" — [madmom discussion #536](https://github.com/CPJKU/madmom/discussions/536)
- The main branch `setup.py` declares `version = '0.17.dev0'`, `install_requires` = `numpy>=1.13.4`, `scipy>=1.13`, `mido>=1.2.6`, Cython extension modules `madmom.audio.comb_filters`, `madmom.features.beats_crf`, `madmom.ml.hmm`, `madmom.ml.nn.layers`, classifiers Python 3.9–3.12 only, no `python_requires`, no `pyproject.toml`, and it imports `Extension` from `distutils` — [madmom setup.py (main)](https://raw.githubusercontent.com/CPJKU/madmom/main/setup.py)
- The unreleased 0.17.dev0 changelog section lists nothing about NumPy 2, Cython 3 or Python >3.7 ("Python 3.7 support (#374)" is its newest Python item); the 0.16 section's only live-audio line is "`TempoDetector` can operate on live audio signals (#292)" — [madmom CHANGES.rst](https://raw.githubusercontent.com/CPJKU/madmom/main/CHANGES.rst)
- `DBNBeatTrackingProcessor(min_bpm=55., max_bpm=215., num_tempi=None, transition_lambda=100, observation_lambda=16, correct=True, threshold=0, fps=None, online=False)`; `online`: "Use the forward algorithm (instead of Viterbi) to decode the beats"; `process_online(activations, reset=True)` runs the forward algorithm frame by frame, declares a beat when the argmax state is a beat state and `cur_beat >= last_beat + 60/max_bpm`, carries a `FIXME` that this "skips the first beat", and has no look-ahead; `RNNBeatProcessor(online=True)` switches to unidirectional `BEATS_LSTM` models, a single 2048-sample frame (offline uses 1024/2048/4096 BLSTM) and 12 filter bands; output is 100 frames per second — [madmom features/beats.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/features/beats.py)
- `DBNDownBeatTrackingProcessor(beats_per_bar, min_bpm, max_bpm, num_tempi, transition_lambda, observation_lambda, threshold, correct, fps)` has NO `online` parameter and no `process_online`; `RNNDownBeatProcessor` takes no `online` flag; nothing in the downbeat module is online or causal — decoding is Viterbi over the whole activation sequence; `RNNBarProcessor`/`DBNBarTrackingProcessor` (beat-synchronous downbeat from given beats) are also whole-sequence — [madmom features/downbeats.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/features/downbeats.py)
- madmom's `OnlineProcessor.process()` dispatches to `process_online(data, reset=True)`; the command-line online loop calls each frame with `{'reset': False}` so stateful processors keep state; the live source is `madmom.audio.signal.Stream`, which "handles live (i.e. online, real-time) audio input via PyAudio", blocks on `stream.read(hop_size)`, and `FramedSignalProcessor` must use `origin='stream'` ("the window is located to the right of its reference sample") to always get the last `frame_size` samples — [madmom processors.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/processors.py); [madmom audio/signal.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/audio/signal.py)
- CPU: a user saw 297% CPU on `DBNBeatTracker online -j 1` (2015 MacBook Pro, Python 3.8); the maintainer attributed it to NumPy parallelism, said `-j` does not guarantee one core, and noted madmom bags 8 networks by default but he does "not expect much lower (detection) performance if only 4 or even 2 are used" (Oct–Nov 2022) — [madmom issue #507](https://github.com/CPJKU/madmom/issues/507)

**madmom-onnx (fork, PyPI)**
- Version 0.17.dev0 uploaded 2026-02-24, sdist only (no wheels); requires numpy>=1.13.4, scipy>=1.13, mido>=1.2.6, onnxruntime>=1.19.2; "Python 3.9 or newer"; replaces the pickle-based NumPy NN inference with ONNX Runtime (`.onnx` model files), but Cython is still a prerequisite and `.pyx` extensions are still built; benchmarks on a 3m45s file: BeatTracker 5.33 s → 4.30 s (1.24×), TCNTempoDetector 5.08 s → 1.77 s (2.88×); NumPy 2 support not mentioned; licence BSD + CC BY-NC-SA models — [madmom-onnx PyPI JSON](https://pypi.org/pypi/madmom-onnx/json). **BeatNet (Heydari, Cwitkowitz & Duan, ISMIR 2021) — online joint beat/downbeat/meter**
- Modes: `stream` (microphone via PyAudio), `realtime` (file, chunk by chunk, causal), `online` (same causal algorithm, reads the file faster, "identical outcomes to the real-time mode"), `offline` (non-causal DBN); inference `PF` (particle filtering, causal) or `DBN` (madmom's, non-causal); three pre-trained CRNN models (1 = GTZAN, 2 = Ballroom, 3 = Rock Corpus); requires librosa and madmom; README says "madmom 0.16.1 has compatibility issues with Python >= 3.10 and NumPy >= 1.24" and suggests Python 3.9 or patches; PyAudio on Windows via a third-party wheel; licence CC-BY-4.0; 529 stars, 11 open issues, no releases on GitHub — [BeatNet GitHub](https://github.com/mjhydri/BeatNet)
- PyPI: BeatNet 1.1.3, released Nov 28 2023, pure-Python wheel, no `Requires-Python`, no licence field — [BeatNet on PyPI](https://pypi.org/project/BeatNet/); its `requires_dist` is exactly `numpy`, `cython`, `librosa >=0.8.0`, `numba ==0.54.1`, `scipy`, `mido >=1.2.6`, `pytest`, `madmom` (unpinned — so `pip install BeatNet` resolves to the broken 2018 madmom 0.16.1 sdist), `torch` (unpinned), `Matplotlib`; `pyaudio` is not declared — [BeatNet PyPI JSON](https://pypi.org/pypi/BeatNet/json)
- Code facts: `BeatNet(model, mode='online', inference_model='PF', plot=[], thread=False, device='cpu')`; sample rate 22050 Hz; hop 441 samples (20 ms), window 1411 samples (64 ms), fps 50; `stream` mode opens PyAudio internally with `frames_per_buffer = hop`; `realtime` accepts a NumPy array but takes the whole array and slices it internally (no public chunk-push API — feeding live chunks from another stream "would require modifying the class"); a source comment says the streaming window setup "adds a 0.084 s delay relative to the training setup, and that this needs fixing"; stream mode emits zeros for the first 5 hops; the threaded path passes `args=(self.pred)` (not a tuple) and would likely fail — [BeatNet.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/BeatNet.py)
- Particle filter defaults: `particle_size=1500`, `down_particle_size=250`, `min_bpm=55`, `max_bpm=215`, `num_tempi=300`, `min_beats_per_bar=2`, `max_beats_per_bar=4`, `ig_threshold=0.4`, `lambda_b=60`, `lambda_d=0.1`; the state space is madmom's `BarStateSpace`/`BarTransitionModel` (`BarStateSpace(1, min_interval, max_interval, num_tempi)` with `min_interval = 60*fps/max_bpm`); initial particles are uniform over states (no explicit prior distribution); frames with max activation < 0.4 are floored to 0.03 (the "information gate"); a downbeat is emitted when the dominant downbeat particle sits in the first-beat states and downbeat activation > 0.4, else a beat when gated activation > 0.4; `process()` returns rows `[time_seconds, label]` (1 = downbeat, 2 = beat) — [particle_filtering_cascade.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/particle_filtering_cascade.py)
- Paper timing: per frame, preprocessing 0.12 ms and network forward pass 0.01 ms; inference for a 30-s excerpt 5.23 s (1000 particles) or 8.87 s (1750 particles) vs 21.30 s for the earlier DLB model, measured on a Windows machine with an AMD Ryzen 9 3900X; runtime grows roughly linearly with particle count — [BeatNet paper (ar5iv)](https://ar5iv.labs.arxiv.org/html/2108.03576)

**BeatNet+ (TISMIR, published Dec 6 2024)**
- Adds an auxiliary non-percussive training branch (MSE between latent embeddings, λ = 200), grows the recurrent block from 2 to 4 LSTM layers (hidden 150), adds adaptation methods "auxiliary freezing (AF)" and "guided fine-tuning (GF)" for isolated singing voice and non-percussive music, releases beat/downbeat annotations for MUSDB18 and URSing; inference is unchanged BeatNet particle filtering; code at github.com/mjhydri/BeatNet-Plus — [BeatNet+ paper](https://transactions.ismir.net/articles/10.5334/tismir.198)
- The BeatNet-Plus repo ships weights `generic_weights.pt`, `generic_main_weights.pt`, `af_non_percussive_weights.pt`, installs via `git clone` + `pip install -e .`, depends on numpy, librosa, madmom, torch, scipy, tensorboard, pyyaml, matplotlib (pyaudio for stream mode), repeats "madmom 0.16.1 has known issues with Python >= 3.10 and NumPy >= 1.24" and suggests Python 3.9; 40 stars, 6 commits; no licence shown — [BeatNet-Plus GitHub](https://github.com/mjhydri/BeatNet-Plus)

**BEAST (Chang & Su, ICASSP 2024) — streaming Transformer**
- "online joint beat and downbeat tracking system based on the streaming Transformer" using contextual block processing and relative positional encoding; "in a low latency scenario with maximum latency under 50 ms" it reports 80.04% beat F1 and 46.78% downbeat F1, "about 5 percentage points over the state-of-the-art online beat tracking model" — [BEAST arXiv](https://arxiv.org/abs/2312.17156)
- The repo provides an evaluation script (`./code/eval.py`), a separately downloaded pretrained model and preprocessed GTZAN data; no microphone/chunked inference demo; MIT; 47 stars, 21 commits, "More information to be updated"; no dependency versions shown — [BEAST GitHub](https://github.com/WildHoneyPie/BEAST)

**Beat This! (Foscarin et al., ISMIR 2024) — offline only**
- The README describes only file-based inference ("predict beats for audio files"); no online, streaming, causal or real-time mode is mentioned; outputs beats AND downbeats; models "About 78 MB per model" (`final*`) or "About 8.1 MB" (`small*`); PyTorch 2.0+; optional madmom for DBN post-processing; MIT code and weights — [beat_this GitHub](https://github.com/CPJKU/beat_this)
- PyPI `beat-this` 1.1.0 released 2026-04-14 (pure-Python wheel), `torch>=2`, `numpy>=1.20`, torchaudio, einops, rotary-embedding-torch, soxr; licence MIT — [beat-this PyPI JSON](https://pypi.org/pypi/beat-this/json)

**AlignBeat (Oct 2025, revised Sep 2026) — newcomer, no online claim**
- "A Latent Variable Model for Multi-Class Beat Tracking from Partially Labeled Data": downbeat CMLt +3.6 points over Beat This!, F-measures within one point; nothing in the abstract addresses causality or real-time use; no code link — [AlignBeat arXiv](https://arxiv.org/abs/2510.14391)

**aubio (upstream) and aubio-ledfx (maintained fork) — causal beat/tempo**
- Upstream aubio PyPI: 0.4.9, released Feb 8 2019, source tarball only (no win_amd64 wheels, no cp310–cp313 builds), GPLv3+ — [aubio on PyPI](https://pypi.org/project/aubio/)
- `aubio-ledfx` 0.4.12 uploaded 2026-10-03, `Requires-Python >=3.11`, "maintained fork of the original aubio project by Paul Brossier, maintained by the LedFx team" because "The original aubio project is no longer actively maintained with regular releases"; wheels for CPython 3.11–3.15 on Linux x86_64/ARM64, macOS Intel/Apple Silicon and Windows AMD64, e.g. `aubio_ledfx-0.4.12-cp312-cp312-win_amd64.whl`, `...-cp313-cp313-win_amd64.whl`, `...-cp314-cp314-win_amd64.whl`; licence GNU/GPL v3 — [aubio-ledfx PyPI JSON](https://pypi.org/pypi/aubio-ledfx/json)
- Fork PR #63 (merged Oct 3 2026, "unbiased beat period, fair phase choice, window sized in time, latency taken back"): before the fix "Every period came out 0.5–0.75 frames short" (160 bpm read as 164.5 at 30000 Hz/hop 500), the window was "the next power of two of 5.8 s of frames" (8.5 s at 30000/500 vs 5.9 s at 44100/512), and "Every beat also came out 20–46 ms late"; after it the window is 5.9 s at any sample rate/hop, "The tempo object now works out its own latency" and fires beats earlier by that amount, residual timing error "within 2 ms on average and 6 ms for 95% of tested settings, with a worst case of 23.5 ms"; beat F-measure on a 160-bpm drum test rose to 1.000; accelerando tempo scores fell from 0.268/0.310 to 0.000 (author attributes it to removing the old bias) — [aubio-ledfx PR #63](https://github.com/LedFx/aubio-ledfx/pull/63); [aubio-ledfx CHANGELOG](https://raw.githubusercontent.com/LedFx/aubio-ledfx/main/CHANGELOG.md)
- Tempo API: `new_aubio_tempo(method, buf_size, hop_size, samplerate)` ("beat tracking method, unused for now (use "default")"), `aubio_tempo_do` returns "output beats" per hop, `aubio_tempo_get_bpm` ("the currently observed tempo, or 0 if no consistent value is found"), `aubio_tempo_get_confidence` ("the higher the more confidence, 0 if no consistent value is found"), `aubio_tempo_get_last` (time of the latest beat, in samples), `set_delay`/`get_delay` (a delay in samples added to the beat time), `set_tatum_signature` (tatums per beat, 1–64); the docs give no algorithm description or reference — [aubio tempo.h docs](https://aubio.org/doc/latest/tempo_8h.html)
- Upstream `tempo.c`: default onset method `specflux`, peak threshold 0.3, silence threshold −90 dB, `winlen = next_power_of_two(5.8 * samplerate / hop_size)`, `step = winlen/4` (beat tracking runs every `step` hops; comment "1.5 seconds"), the ODF is buffered and `aubio_beattracking_do` emits predicted beat positions for the coming hops; a beat is unset "if silent"; `delay` is only added in `get_last` — [aubio tempo.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/tempo.c)
- Upstream `beattracking.c` (copyright 2005-2009 Matthew Davies and Paul Brossier): autocorrelation of the ODF, shift-invariant comb filterbank with 4 teeth (or `timesig` once the "context dependent model" is active), Rayleigh weighting with `rayparam = 60*samplerate/120/hop_size` ("sets preferred tempo to 120bpm"), context model with Gaussian weight `g_var = 3.901` frames around the previous period and a 3-step consistency check before switching, `fvec_gettimesig` picks 3 or 4 beats per bar from comb energies, beat periods below 25 frames are doubled (comment "if tempo is > 206 bpm, half it"), phase from a Gaussian-weighted comb over the buffered ODF, beats written ahead while `beat + bp <= step`; confidence = quadratic peak magnitude of the comb output at the context period divided by the comb sum, 0 until the context model is active; `get_bpm = 60/period` — [aubio beattracking.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/beattracking.c)

**BTrack (Stark, Davies & Plumbley) — causal C++ beat tracker**
- "BTrack is a causal beat tracking algorithm intended for real-time use", C++ with Python and Vamp wrappers, default hop 512 / frame 1024, needs libsamplerate (FFTW or bundled Kiss FFT), GPLv3, release 1.0.7 dated 31 Dec 2025, no downbeat output (`beatDueInCurrentFrame()` only) — [BTrack GitHub](https://github.com/adamstark/BTrack)
- Source: ODF = `ComplexSpectralDifferenceHWR` with Hann window; `onsetDFBufferSize = (512*512)/hopSize` frames (512 frames ≈ 5.9 s at 44.1 kHz/512); tempo range 80–160 BPM in 2-BPM steps (41 tempi; `setTempo`/`fixTempo` fold any tempo into 80–160 with `while (tempo > 160)` / `while (tempo < 80)`); Rayleigh parameter 43; Gaussian tempo transition (`m_sig = 41/8`); `setTempo(bpm)` reseeds the cumulative score with pulses at the new period and marks the current frame as a beat; `fixTempo(bpm)` sets `tempoFixed = true` (a hard tempo prior) and `doNotFixTempo()` releases it; beats are predicted ahead via `timeToNextBeat`/`timeToNextPrediction = timeToNextBeat + round(beatPeriod/2)`; 44100 Hz is hard-coded in `setHopSize` and `calculateTempo` — [BTrack.cpp](https://raw.githubusercontent.com/adamstark/BTrack/master/src/BTrack.cpp)
- PyPI `btrack-beat-tracker` 1.0.7 (2025-12-31), `Requires-Python >=3.8`: wheels only for `cp311`–`cp314` on `macosx_15_0_arm64` plus an sdist that needs CMake 3.15+, a C/C++ compiler, NumPy and libsamplerate; the Python API is whole-array (`detect_beats(audioData)` → beat times in seconds, `calculate_onset_detection_function`, `detect_beats_from_odf`), input mono at 44100 Hz; no `win_amd64` wheel — [btrack-beat-tracker PyPI JSON](https://pypi.org/pypi/btrack-beat-tracker/json)

**essentia — no Windows wheels**
- Latest PyPI pre-release 2.1b6.dev1438 (May 19 2026) lists only `manylinux2014_x86_64` and `macosx_15_0` (x86_64, arm64) wheels for cp314; no Windows wheel, no Windows classifier; licence AGPL-3.0-only — [essentia on PyPI](https://pypi.org/project/essentia/)

### Inferences
- madmom is effectively unmaintained (last release 2017/2018; main branch last pushed Aug 2024 per a search snippet — unverified; open install issues through 2026; PRs #542/#548 unmerged or unreleased). On this laptop it cannot be installed at all until the Microsoft C++ Build Tools (several GB) are installed; even then the community threads only confirm builds on Python 3.11 (Windows, 2023) and "3.12 classifiers" in setup.py — nobody in the threads confirms Python 3.13, and Cython must be pinned (3.0.x or ≥3.1.2) with PR #548 or the `v0.17_fixes` branch applied. Treat madmom as "possible but fragile" and keep it out of the gig-critical path.
- BeatNet and BeatNet+ inherit every madmom problem (they import `madmom.features.beats_hmm`), add PyTorch (~200 MB CPU wheel) and PyAudio, and their stream mode opens its own PyAudio device rather than accepting chunks — so using them would mean: compile madmom, then subclass/patch `BeatNet` to push 20-ms chunks from the existing sounddevice callback. Feasible for one developer, but it is real integration work, not a pip install.
- `aubio-ledfx` is the only candidate that is a pure `pip install` on 3.12/3.13 Windows today, and its Oct 2026 tempo fixes (timestamps within ~2 ms mean / 6 ms p95) make its beat times trustworthy for clock alignment. Its weaknesses are algorithmic (no tempo range/prior API, preferred tempo fixed at 120 BPM, octave errors — see Q6 benchmark), not packaging.
- BTrack's algorithm is the same family as aubio's (Davies' context-dependent comb-filter tracker) and uniquely exposes `fixTempo()`, but the PyPI binding is whole-array and has no Windows wheel; re-implementing its cumulative-score predictor in numpy is less work than building it on Windows.
- BEAST is research code (eval script only); not a deployable option.
- Beat This! is the right tool for the OFFLINE job: annotate each stored reference recording with beats + downbeats once, producing the bar map the live tracker is aligned to (see Q8).
- `aubio-ledfx` requires Python >=3.11 while the suite declares Python >=3.10: adopting it means raising the project floor to 3.11 (the laptop already runs 3.12) or shipping the tracker as an optional extra.

## Q2. Accuracy on pop/rock (F-measure, CMLt/AMLt) for the ONLINE variants, and online-vs-offline latency

### Takeaway
On GTZAN (the shared benchmark), online beat F1 is 74–81% ("Böck FF" 74.2 — interpreted here as madmom's forward-algorithm online tracker, see Inferences — BeatNet 75.4, BEAST 80.0, BeatNet+ 80.6) versus 79–89% offline, while online DOWNBEAT F1 is only 46–57% versus 71–76% for offline transformers; on the Rock Corpus BeatNet online scores 73.1 beat / 45.0 downbeat. Reported latencies are one STFT hop: 20 ms (BeatNet/BeatNet+), 46 ms (madmom online, BEAST), 23 ms (IBT); no CMLt/AMLt figures for online systems were found.

### Cited Findings
- BeatNet paper, Table 2 (F-measure, ±70 ms), GTZAN online: BeatNet 75.44 beat / 46.49 downbeat; Aubio 57.09; Böck ACF 64.63; "Böck FF [20, 6]" 74.18 (the paper's own label; its reading as madmom's online forward-algorithm tracker is an inference, below); DLB (Heydari & Duan ICASSP 2021) 73.77; IBT 68.99. GTZAN offline: BeatNet+DBN 80.64 / 54.07; Böck (madmom offline) 79.09 / 51.36. Ballroom online: BeatNet 77.41 / 47.45, Aubio 56.73, IBT 70.79. Rock Corpus online (Rock held out of training): BeatNet 73.13 / 44.98, Aubio 59.83, IBT 68.55. BeatNet online trails offline madmom by 3.65 points on beats and 4.9 on downbeats; no CMLt/AMLt reported — [BeatNet paper (ar5iv)](https://ar5iv.labs.arxiv.org/html/2108.03576)
- BeatNet+ paper, Table 2 (GTZAN full mixtures, 70 ms): BeatNet+ 80.62 / 56.51, latency 20 ms, RTF 0.08; BeatNet+ (Solo) 78.43 / 49.74; BeatNet 75.44 / 46.69, 20 ms, RTF 0.06; "Novel 1D" 76.47 / 42.57, 20 ms, RTF 0.02; IBT 68.99 / –, 23 ms, RTF 0.16; Böck FF 74.18 / –, 46 ms, RTF 0.05; BEAST 80.04 / 52.23, 46 ms, RTF 0.40; offline references Transformers 88.5 / 71.4 and SpecTNT-TCN 88.7 / 75.6; "Latency is defined as the STFT hop size"; RTFs measured on a Windows machine with an AMD Ryzen 9 3900X at 3.80 GHz; the text claims BeatNet+ is "nearly seven times" faster than BEAST though the table ratio is ≈5× — [BeatNet+ paper](https://transactions.ismir.net/articles/10.5334/tismir.198)
- BEAST abstract: 80.04% beat F1 and 46.78% downbeat F1 "in a low latency scenario with maximum latency under 50 ms" — [BEAST arXiv](https://arxiv.org/abs/2312.17156)
- madmom online specifics: `RNNBeatProcessor(online=True)` uses one 2048-sample frame (46.4 ms at 44.1 kHz) and unidirectional LSTMs instead of the offline BLSTM ensemble over 1024/2048/4096 frames; the online DBN uses the forward algorithm with no look-ahead — [madmom features/beats.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/features/beats.py)
- BeatNet code adds a stated 0.084 s delay in the streaming window setup on top of its 20 ms hop, and emits zeros for the first 5 hops — [BeatNet.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/BeatNet.py)
- aubio-ledfx (post-PR-#63) beat timestamps: residual error "within 2 ms on average and 6 ms for 95% of tested settings, with a worst case of 23.5 ms" (before the fix beats were 20–46 ms late) — [aubio-ledfx PR #63](https://github.com/LedFx/aubio-ledfx/pull/63)
- A May 2026 failure-mode study of state-of-the-art (DBN-post-processed) trackers finds octave errors, continuity errors and complete failures, "confident-but-wrong" activations, and that the DBN's default minimum tempo of 55 BPM prevents correct inference for 21% of SMC tracks, forcing double-tempo predictions on slow music — [SMC Blind Spot arXiv](https://arxiv.org/abs/2605.12287)

### Inferences
- "Böck FF" is interpreted in these notes as madmom's online tracker (online RNN + forward-algorithm DBN). Neither paper says so explicitly; the supporting evidence is that the BeatNet+ table gives that row a 46 ms latency, which equals madmom's 2048-sample online frame at 44.1 kHz, and madmom documents `online=True` as "Use the forward algorithm (instead of Viterbi)". Treat the 74.18 / 46 ms / RTF 0.05 figures for madmom as "probable", not confirmed.
- The offline→online penalty is modest for beats (~4–9 F1 points) but large for downbeats (~20 points): online systems get barely more than half of GTZAN downbeats right. For a bar-based app this is the single most important number: audio-only online downbeat detection is not reliable enough to set the bar phase by itself.
- GTZAN is 30-s excerpts across ten genres; pop/rock subsets are not reported separately. The Rock Corpus row (73.1 beat / 45.0 downbeat online) is the closest proxy for cover-band material and is slightly below the GTZAN average, probably because rock mixes have syncopated and half-time feels.
- "Latency = hop" is the algorithmic floor; real end-to-end latency adds the analysis frame (madmom's 46 ms frame, BeatNet's 64 ms window + 84 ms streaming offset), the audio block size and the interface's input latency (Q8). Reported beat times, however, refer to the audio position, so a late REPORT does not make the TIMESTAMP wrong — what matters for the clock is timestamp error (aubio-ledfx: ~2 ms mean), not report delay.

### Gaps
- No CMLt/AMLt (continuity) figures for any online tracker were found; those metrics would tell how often the tracker sits on the off-beat or at half/double tempo, which matters more to this app than F1.
- No published evaluation of online trackers on live-concert recordings (room, bleed, PA) was found; all numbers are studio/album excerpts.
- No numbers exist for the typical delay between a band's first downbeat and the first CORRECT online downbeat (see Q3).

## Q3. Online downbeat (bar) tracking: which tools, how reliable in 4/4 pop/rock, how long to lock

### Takeaway
Only BeatNet/BeatNet+ (particle filter) and BEAST do downbeats causally; madmom's downbeat tracker is offline-only. Online downbeat F1 on GTZAN is 46–57% (Rock Corpus 45%), i.e. roughly a coin flip per bar, and no source quantifies lock-in time in bars; the app must anchor the bar phase from something else (the tap, a count-in, or alignment to the reference recording) and use audio downbeat evidence only to confirm or nudge it.

### Cited Findings
- madmom `DBNDownBeatTrackingProcessor` has no `online` parameter and only whole-sequence Viterbi `process()`; the bar-tracking processors are also whole-sequence — [madmom features/downbeats.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/features/downbeats.py)
- BeatNet runs two cascaded particle filters (1500 beat particles, 250 downbeat/meter particles); "Downbeat particles are initialized when the first beat is detected"; convergence is shown only qualitatively (Figure 3 walkthrough); meter values from 2 upward — [BeatNet paper (ar5iv)](https://ar5iv.labs.arxiv.org/html/2108.03576)
- BeatNet code emits a downbeat only when the dominant downbeat particle is in the first-beat states, the previous label was not a downbeat, and the downbeat activation exceeds 0.4; `beats_per_bar=[]` by default with `min_beats_per_bar=2`, `max_beats_per_bar=4` (settable to `[4]` for fixed 4/4) — [particle_filtering_cascade.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/particle_filtering_cascade.py)
- Online downbeat F1: BeatNet 46.49–46.69 (GTZAN), 47.45 (Ballroom), 44.98 (Rock Corpus); BeatNet+ 56.51 (GTZAN); BEAST 46.78 (abstract) / 52.23 (as re-reported in BeatNet+); offline: madmom 51.36, BeatNet+DBN 54.07, Transformers 71.4, SpecTNT-TCN 75.6 — [BeatNet paper](https://ar5iv.labs.arxiv.org/html/2108.03576); [BeatNet+ paper](https://transactions.ismir.net/articles/10.5334/tismir.198); [BEAST arXiv](https://arxiv.org/abs/2312.17156)
- aubio's context model infers a time signature of 3 or 4 from comb energies (`fvec_gettimesig`) but exposes no downbeat output; BTrack reports beats only — [aubio beattracking.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/beattracking.c); [BTrack GitHub](https://github.com/adamstark/BTrack)

### Inferences
- Because the BeatNet downbeat filter starts only after the first beat and must then disambiguate 2–4 beats per bar from accents, it cannot lock in less than one bar and in practice needs several bars of clear kick/snare pattern; with ~50% F1 it will also flip phase mid-song on fills and breakdowns. Expect it to be useful as a "vote", not a source of truth.
- In 4/4 pop/rock the strongest bar cue is the kick-on-1 / snare-on-2-and-4 pattern plus chord changes on bar lines; a cheap low-band/snare-band onset pattern matcher restricted to a known 4-beat period (Q6) will give comparable or better evidence for THIS repertoire than a general-purpose network, because the problem is reduced to choosing one of four phases.
- The app already has two far stronger bar anchors: the guitarist's tap (two bars) and the reference recording (a bar map produced offline with Beat This!). Lock the bar phase from those; let the live tracker own only tempo and beat phase.

### Gaps
- No paper or README quantifies online downbeat lock-in time (bars) or phase-flip frequency; the only description is BeatNet's qualitative figure.
- No per-genre breakdown of online downbeat accuracy for pop/rock beyond the Rock Corpus row.

## Q4. Using the setlist BPM as a tempo prior

### Takeaway
madmom and BeatNet take the prior as a hard range (`min_bpm`/`max_bpm`, with `num_tempi` controlling resolution), BTrack has `fixTempo()`/`setTempo()`, librosa's `bpm=` is offline-only, and aubio has NO tempo-range API (its Rayleigh prior is hard-wired to prefer 120 BPM), so with aubio the prior must be applied in app code by folding octave errors. No paper quantifies how much a ±10% range shortens lock time, but a narrow range removes the octave and off-beat ambiguities that dominate online errors and shrinks the DBN/particle state space proportionally.

### Cited Findings
- madmom: `DBNBeatTrackingProcessor(min_bpm=55., max_bpm=215., num_tempi=None, transition_lambda=100, ...)` — `num_tempi`: "if set, limit the number of tempi and use a log spacing, otherwise a linear spacing"; `transition_lambda`: higher values favour a constant tempo between consecutive beats; the online beat-acceptance rule uses `60/max_bpm` as the minimum inter-beat interval — [madmom features/beats.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/features/beats.py)
- BeatNet: `particle_filter_cascade(beats_per_bar=[], particle_size=1500, down_particle_size=250, min_bpm=55., max_bpm=215., num_tempi=300, ...)`; the range becomes `min_interval = 60*fps/max_bpm`, `max_interval = 60*fps/min_bpm` in a madmom `BarStateSpace`; initial particles are uniform over the states; the `BeatNet` constructor builds the estimator with only `beats_per_bar=[]`, `fps=50`, so a prior requires constructing/patching the estimator yourself — [particle_filtering_cascade.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/particle_filtering_cascade.py); [BeatNet.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/BeatNet.py)
- BTrack: `fixTempo(tempo)` sets `prevDeltaFixed[tempoIndex] = 1; tempoFixed = true;`, `setTempo(tempo)` reseeds the cumulative score at the new period, `doNotFixTempo()` releases; both fold the tempo into 80–160 BPM (2-BPM grid) — [BTrack.cpp](https://raw.githubusercontent.com/adamstark/BTrack/master/src/BTrack.cpp)
- aubio: `rayparam = 60*samplerate/120/hop_size` ("sets preferred tempo to 120bpm"), no min/max BPM parameter in `new_aubio_tempo(method, buf_size, hop_size, samplerate)`; periods under 25 frames are doubled — [aubio beattracking.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/beattracking.c); [aubio tempo.h docs](https://aubio.org/doc/latest/tempo_8h.html)
- librosa `beat_track(bpm=...)`: "if provided, use bpm as the tempo instead of estimating it" — offline DP only — [librosa beat.py](https://raw.githubusercontent.com/librosa/librosa/main/librosa/beat.py)
- Evidence that the tempo range matters: the DBN's default 55 BPM minimum alone caused wrong (double-tempo) inference on 21% of SMC tracks — [SMC Blind Spot arXiv](https://arxiv.org/abs/2605.12287)
- First-hand benchmark (Q6): with no prior, aubio-ledfx locked a synthetic 148-BPM full mix within 1.5 s but switched to 74 BPM (half tempo) after ~11 s and stayed there; the guitar-only signal held 148 — embedded log in Q6.

### Inferences
- For madmom/BeatNet, set `min_bpm = 0.85·BPM`, `max_bpm = 1.15·BPM` (covers "5–10% off the record" with margin) and `num_tempi` ≈ 30–60; this cuts the state space from ~160 BPM of range to ~45 BPM, so the DBN/particle filter runs proportionally faster and cannot produce ×2/÷2 or 3:2 errors at all. Also raise `transition_lambda` (madmom) when the drummer plays to a click (Q5).
- For aubio (no API), apply the prior AFTER the fact: `bpm_est = get_bpm()`; fold by ×2, ÷2, ×3/2, ×2/3 into [0.85, 1.15]·BPM; if nothing folds in, mark "unlocked". Note that when aubio halves the tempo it also emits only every other beat (first-hand test: 39/60 beats matched), so the app must interpolate the missing beats from the folded period, or hand-roll the tracker (Q6) so the ambiguity never arises.
- Lock-time benefit: with a ±10% window the comb/ACF peak search covers ~3 lags at a 5.9-s window, so a stable estimate exists as soon as 2–3 beat periods of onsets are in the buffer (≈1 bar at 148 BPM) instead of waiting for the broad-range peak to dominate its octave neighbours; the first-hand test shows aubio itself already reports a tempo within 2% at 1.49 s (its first `step`). The remaining lock cost is beat PHASE, which needs one or two more beats.

### Gaps
- No published experiment measures lock time or accuracy as a function of tempo-range width for any tracker; the "±10% improves X" question has no quantitative answer in the literature found.
- Whether BeatNet's accuracy improves with a narrowed range is untested here (it could not be installed without the compiler).

## Q5. Behaviour with and without a click track; count-ins, drumless intros, stops and false starts

### Takeaway
No source evaluates trackers specifically on click-vs-no-click, count-ins or breaks; what the code shows is that madmom (`reset`) and aubio (silence gate, no state reset API) can be restarted per song, BeatNet's stream loop has no reset, and all three keep predicting through silence from their last state. The design consequence is that the app, not the tracker, must own the "locked / free-running / unlocked" state machine.

### Cited Findings
- madmom `process_online(activations, reset=True)`: "Reset the DBNBeatTrackingProcessor to its initial state before processing"; the online loop passes `reset=False` to keep state; the `FIXME` notes the first beat is skipped because `last_beat` starts at 0 — [madmom features/beats.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/features/beats.py); [madmom processors.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/processors.py)
- madmom `transition_lambda` (default 100): "Higher values favor a constant tempo between consecutive beats" — [madmom features/beats.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/features/beats.py)
- aubio: `silence = -90 dB` default; `tempo->data[0] = 0; // unset beat if silent`; the ODF window is 5.9 s (post-fix) and the tracker re-evaluates every `step = winlen/4` (≈1.5 s); the context model needs a 3-step consistency check before it changes period — [aubio tempo.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/tempo.c); [aubio beattracking.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/beattracking.c); [aubio-ledfx PR #63](https://github.com/LedFx/aubio-ledfx/pull/63)
- BeatNet stream mode is an endless `while` loop reading PyAudio hops; the information gate floors frames with activation < 0.4 to a constant likelihood 0.03 and skips resampling (i.e. the particles coast through silence) — [BeatNet.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/BeatNet.py); [particle_filtering_cascade.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/particle_filtering_cascade.py)
- BeatNet+ calls isolated singing voice "the most challenging task among all discussed in this work" and non-percussive music "another challenging task"; its AF model beats base BeatNet on drum-removed GTZAN by 8.88 / 8.19 points at 70 ms — [BeatNet+ paper](https://transactions.ismir.net/articles/10.5334/tismir.198)
- First-hand drift test (Q6 log): with the band speeding up 5% over 24 s and no click, aubio-ledfx followed the tempo (147→153.5 BPM on the guitar-only signal) with beats on average 10–11 ms late (the 5.9-s window averages the accelerating tempo); on the full mix it again halved to ~75 BPM but kept tracking the drift at half tempo.

### Inferences
- With a click: tempo is a constant known to the band; store the CLICK BPM per song (it may differ from the album BPM used for the clock ratio), set the range to ±3% and `transition_lambda` high (or in a hand-rolled tracker simply fix the period and estimate phase only). The problem reduces to phase + downbeat, which the tap already solves; the tracker's job becomes drift correction of the tap over minutes.
- Without a click: real bands drift and lurch (chorus push, ending rallentando); keep the ±10–15% range, a 4–8 s tempo window and per-beat phase correction. Tempo lag of ~10 ms per beat under a 5%-per-song accelerando (first-hand) is negligible for lyrics/part maps but not for tight effect cues; cue timing should be scheduled from the phase-corrected clock, not from the raw tempo estimate.
- Count-ins: stick clicks are ideal onsets, but a 4-count at 148 BPM lasts 1.6 s, exactly one aubio `step`, so the tracker will have a tempo but at most one or two beats by the time the band enters. Use the count-in as a bar anchor by convention (the beat after the fourth click is "1") only if the app can see four isolated clicks at the expected period; otherwise rely on the tap.
- Drumless intros (Free Bird, acoustic strums): ODF-based trackers can follow regular strumming (first-hand synthetic test), but sustained chords and lead lines give weak, irregular onsets; expect "unlocked" until the drums enter and treat the first strong kick/snare pattern as the re-lock point. BeatNet+'s non-percussive model is the only learned option tuned for this, and it is not pip-installable on Windows today.
- Stops/breaks/false starts: define lock states from evidence, e.g. LOCKED (≥6 consecutive beats with onsets within ±40 ms of prediction), COASTING (predictions continue at last tempo, no onsets for ≤2 bars), UNLOCKED (no onsets > 2 bars or inter-beat intervals inconsistent). On UNLOCKED reset the tracker (`reset=True` in madmom; re-create the aubio object; re-init a hand-rolled buffer) and require the tap or a fresh lock before trusting bars again; on a false start the tap remains the restart gesture.

### Gaps
- No quantitative literature on click-vs-no-click tracking accuracy, typical live tempo drift, or recovery time after a break was found. Everything above the "Cited Findings" line in this section is design inference from code behaviour and a synthetic test.

## Q6. The cheap alternative: onset detection + autocorrelation/comb filter around the known BPM, with a beat-phase estimator

### Takeaway
This is exactly what aubio and BTrack already are (spectral-flux/complex-difference ODF → ACF/comb filter → predicted beats), they cost well under 1% of one core, and with a ±10% tempo window around the setlist BPM the main failure mode of the general version (octave errors — observed first-hand) disappears; it is good enough for a drummed 4/4 cover set with a strong prior and a tap fallback, and it cannot by itself deliver downbeats, drumless intros or syncopated half-time feels, which are the cases where an RNN/particle-filter tracker earns its install cost.

### Cited Findings
- aubio pipeline and constants: default ODF `specflux`, threshold 0.3, window 5.9 s, re-estimation every ~1.5 s, 4-tooth comb over the ODF autocorrelation with Rayleigh prior at 120 BPM, context Gaussian with σ = 3.901 frames, phase from a Gaussian-weighted comb, beats predicted ahead within the step — [aubio tempo.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/tempo.c); [aubio beattracking.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/beattracking.c)
- BTrack pipeline: `ComplexSpectralDifferenceHWR` ODF at hop 512 / frame 1024, 512-frame (≈5.9 s) ODF buffer, comb filterbank with Rayleigh parameter 43 over 128 lags, 41 tempi 80–160 BPM, Gaussian tempo transition, cumulative score with `timeToNextBeat` prediction, `fixTempo` — [BTrack.cpp](https://raw.githubusercontent.com/adamstark/BTrack/master/src/BTrack.cpp)
- Accuracy of the cheap trackers without a prior, online, GTZAN: Aubio 57.09 beat F1, Böck ACF 64.63, IBT 68.99 vs 74–81 for the RNN trackers; Rock Corpus: Aubio 59.83, IBT 68.55 vs BeatNet 73.13 — [BeatNet paper (ar5iv)](https://ar5iv.labs.arxiv.org/html/2108.03576); IBT latency 23 ms, RTF 0.16 — [BeatNet+ paper](https://transactions.ismir.net/articles/10.5334/tismir.198)

### Inferences
- CPU: an ODF at hop 512 (one 1024-point FFT every 11.6 ms) plus a comb/ACF search every 0.5–1.5 s is ~0.2% of a core in aubio's C implementation and will stay below ~2% in plain numpy (one `np.fft.rfft` per hop, vectorised comb over ~3–10 lags, phase comb over ≤8 beats). - Latency: beats are PREDICTED ahead (aubio writes upcoming beat positions within the next 1.5-s step; BTrack counts down `timeToNextBeat`), so the clock can be scheduled slightly ahead of real time — effectively zero or negative reporting latency once locked; timestamp error ≈2–4 ms (first-hand, steady tempo) to ≈10 ms (5% accelerando). Lock: tempo within 2% after the first 1.5-s analysis step, first beat emitted at ~1.6 s (≈4 beats / 1 bar at 148 BPM).
- The observed octave error (full mix → 74 BPM at ~11 s, then only every other beat emitted) is the characteristic failure of broad-range comb trackers on kick/snare backbeats (the 2-beat kick–snare cycle competes with the beat period). A hand-rolled version that evaluates the comb/ACF only at lags within ±10–15% of 60/BPM_setlist cannot make this error, which is why "hand-rolled numpy with the prior" is preferable to "aubio as-is" for this app even though aubio is a one-line install. Keep aubio-ledfx as the ODF provider (its `specdesc`/`onset` objects) or as a quick prototype with post-hoc octave folding.
- Good enough when: drums present, 4/4, tempo within ±15% of the stored BPM, the tap or reference alignment supplies the bar phase, and the app only needs beat phase + tempo + a confidence. Not good enough when: drumless/rubato intros, songs with half-time/double-time sections (the prior must switch with the song-part map — the app knows the part map, so it can switch the expected period per section), or when the app must find "1" with no anchor at all; those are the cases for BeatNet+/BEAST-class models, which still only reach ~50–56% downbeat F1 online.
- Recommended concrete recipe (numpy, ~150 lines): (1) mono float32 at the interface rate (44.1/48 kHz), hop 512, frame 1024 Hann → log-magnitude spectrum → half-wave-rectified spectral flux, optionally in 3 bands (kick <150 Hz, snare 150–2 kHz, hats >2 kHz) kept separately for the bar matcher; (2) keep an ODF ring buffer of ~8 s (≈690 frames at 86 fps); (3) every 0.5 s compute the ACF (or a 3-tooth comb) only for lags in [60/(1.15·BPM), 60/(0.85·BPM)] seconds, parabolic-interpolate the peak, require peak/mean ratio above a threshold for 2 consecutive evaluations → tempo lock in ≈2 bars; (4) phase: for the locked period P, project the last 8 beats of ODF onto candidate phases (shift-and-sum), argmax → next beat time; emit predicted beat times ahead, correct phase per beat with a gain of ~0.3–0.5 (an alpha filter) so single fills do not yank the clock; (5) bar matcher: with P locked and 4 beats/bar, score the 4 candidate bar phases by kick-band energy on beat 1 and snare-band energy on beats 2 and 4 over the last 4–8 bars; only ever use it to CONFIRM or flag the tap/alignment bar phase, never to override it silently; (6) confidence = min(peak/mean ratio of the tempo comb, fraction of last 8 predicted beats with an ODF peak within ±40 ms, 1 − |IBI jitter|/P) → publish to the API; below threshold for > 1 bar → UI says "tap".

### Gaps
- The benchmark signal is synthetic (perfectly regular strums, no bleed, no vocals); real-mix numbers for aubio-ledfx with the prior-folding logic are not available and must come from the developer's own gig recordings.
- No published comparison of "comb filter with a strong prior" vs RNN trackers exists; the claim that the prior closes most of the 57→75 F1 gap for drummed pop/rock is inference, consistent with the SMC paper's finding that range errors are a large share of DBN failures.

## Q7. Guitar-only feed vs full band mix

### Takeaway
Direct evidence is thin: the only quantitative source (BeatNet+) shows non-percussive mixes are "challenging" and that a model adapted to them gains 8–13 F1 points over base BeatNet, implying a large base-model loss once drums are removed; a first-hand synthetic test shows an ODF tracker follows regular strummed chords with lower tempo confidence (0.4 vs 1.4) but no octave error, while sustained chords and lead lines will give little usable onset information. Prefer the full mix (or at least a drum/room mic) for tracking; use the guitar feed only as a fallback.

### Cited Findings
- BeatNet+ on GTZAN with drums removed: AF improves on BeatNet by "8.88% and 8.19%" at 70 ms and "10.55% and 12.85%" at 200 ms (beat and downbeat; the paper's own ordering has a typo), reported only as plots; the authors call singing voice "the most challenging task" and non-percussive analysis "another challenging task" — [BeatNet+ paper](https://transactions.ismir.net/articles/10.5334/tismir.198)
- BeatNet+ ships `af_non_percussive_weights.pt` for the drumless case — [BeatNet-Plus GitHub](https://github.com/mjhydri/BeatNet-Plus)
- aubio's confidence is the comb peak over the comb sum at the context period — a periodicity-strength measure; in the first-hand test it read ≈1.38–1.41 on the drummed mix while the tempo was right (7.5–9.5 s) and ≈1.2 after it had dropped to the wrong octave (74 BPM), versus ≈0.4 on the drumless strums at the right tempo, so it measures periodicity strength, not correctness — [aubio beattracking.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/beattracking.c) and the Q6 log
- First-hand (Q6 log): guitar-only synthetic strums: 56/60 beats matched, |err| 3.4 ms, tempo held at 147.6 for 24 s; full mix: octave error after 11 s.

### Inferences
- A rhythm-guitar DI with steady down/up strums is a clean onset source (every strum is a transient) and the comb tracker handles it; the real problems are (a) lead/solo sections and sustained power chords (Free Bird solo, Sultans fills) where onsets are sparse or syncopated and (b) the guitarist's own timing errors becoming the clock's errors. With the band mix, the drums dominate the ODF and the guitarist's part is irrelevant to tracking.
- If the interface only carries the guitar, feed the tracker but weight its confidence down and lean on the tap and the song-part map; if the interface can take a second channel (a room/overhead mic), that channel is worth far more to the tracker than the DI.
- The guitar-only case also makes the bar matcher (kick/snare pattern) useless; bar phase must come from tap/alignment.

### Gaps
- No paper evaluates beat tracking on isolated electric-guitar stems; the drum-removed GTZAN figures (plots only, absolute values not extracted) are the nearest evidence.
- No evidence on amp-modelled vs DI signals; expected to be irrelevant to onset detection but unverified.

## Q8. Integration: frame/hop rates, buffers, timestamping beats against the interface clock, and fusing beat phase with position tracking in one clock

### Takeaway
Tap the existing sounddevice `InputStream` callback (do not open a second device), push blocks with their `time.inputBufferAdcTime` into a queue, run the tracker in its own thread at hop 512 (≈11 ms), and express every beat as an ADC-clock time; map ADC time to the app clock with a running offset, and fuse three sources — tracker (tempo + beat phase, continuous), tap (bar anchor, explicit), reference alignment (bar position, slow) — in one song-clock state with a confidence that gates the fallback.

### Cited Findings
- sounddevice callback: the `time` argument is "a CFFI structure with timestamps indicating the ADC capture time of the first sample in the input buffer (`time.inputBufferAdcTime`), the DAC output time of the first sample in the output buffer (`time.outputBufferDacTime`) and the time the callback was invoked (`time.currentTime`). These time values are expressed in seconds and are synchronised with the time base used by `time` for the associated stream"; `Stream.time` is "The current stream time in seconds" on "the same clock used to generate the timestamps", "monotonically increasing and have unspecified origin"; `Stream.latency` "provides the most accurate estimate of input/output latency available to the implementation" and "may differ significantly from the latency value(s) passed to Stream()"; `blocksize=0` (default) lets the callback "receive an optimal (and possibly varying) number of frames"; `latency='high'` (default) "is typically more robust (i.e. buffer under-/overflows are less likely)"; the fifth callback argument is a `CallbackFlags` "indicating whether input and/or output buffers have been inserted or will be dropped to overcome underflow or overflow conditions" — [python-sounddevice streams API](https://python-sounddevice.readthedocs.io/en/latest/api/streams.html)
- madmom's own live path opens a PyAudio `Stream` and blocks on `stream.read(hop_size)`; BeatNet's stream mode opens PyAudio with `frames_per_buffer = hop`; both are their own audio clients — [madmom audio/signal.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/audio/signal.py); [BeatNet.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/BeatNet.py)
- Analysis rates used by the trackers: madmom 100 fps (10 ms hop), online frame 2048 samples; BeatNet 22050 Hz, hop 441 (20 ms), window 1411 (64 ms), fps 50; aubio/BTrack hop 512, frame 1024 at 44.1 kHz (11.6 ms) with a 5.9-s ODF window; BeatNet `realtime` arrays "are not resampled, so they must already be at 22050 Hz"; BTrack hard-codes 44100 Hz — [madmom features/beats.py](https://raw.githubusercontent.com/CPJKU/madmom/main/madmom/features/beats.py); [BeatNet.py](https://raw.githubusercontent.com/mjhydri/BeatNet/main/src/BeatNet/BeatNet.py); [aubio tempo.c](https://raw.githubusercontent.com/aubio/aubio/master/src/tempo/tempo.c); [BTrack.cpp](https://raw.githubusercontent.com/adamstark/BTrack/master/src/BTrack.cpp)
- aubio-ledfx now sizes its window in seconds for any sample rate/hop and compensates its own latency (so 48-kHz interfaces are fine) — [aubio-ledfx PR #63](https://github.com/LedFx/aubio-ledfx/pull/63)
- Beat This! produces beats and downbeats offline for whole files (MIT, `pip install beat-this`, torch ≥ 2) — the tool for annotating the stored reference recording — [beat_this GitHub](https://github.com/CPJKU/beat_this); [beat-this PyPI JSON](https://pypi.org/pypi/beat-this/json)

### Inferences
- Audio plumbing: one `sounddevice.InputStream` already exists for the wake word; WASAPI-exclusive/ASIO devices commonly refuse a second client, and two streams would have two clocks, so the tracker must consume the same callback. In the callback do only: copy block → `queue.put((block, time.inputBufferAdcTime, flags))`; a worker thread accumulates into a ring buffer and runs the ODF per 512-sample hop. Whisper and the tracker then share one capture with zero extra device latency.
- Timestamping: a beat placed at hop index k (sample s = k·512 + offset within hop) in the ring buffer gets `t_adc = adc_time_of_block_start + (s − block_start_sample)/fs`, i.e. the time the sample was captured, which already excludes interface input latency and OS buffering. Keep a running estimate `offset = perf_counter() − stream.time` (median over the last few seconds; the PortAudio clock and the PC clock drift apart only slowly) to express `t_wall = t_adc + offset`; publish beats as `(t_wall, beat_index_in_bar, tempo, confidence)` over the API so the stage view, lyrics scroller and pedal cue scheduler all use one time base. Handle `flags` overflow by marking a discontinuity and resetting the tracker buffer.
- Rates: 44.1 or 48 kHz as the interface runs; hop 512 → ~86–94 ODF fps, far finer than a 16th note at 148 BPM (101 ms); block size 256–1024 (`latency='low'` ≈ 5–20 ms on WASAPI) — the tracker does not need small blocks; the wake-word stream's existing blocksize can stay. If BeatNet/madmom are ever used, resample a copy of the feed to 22.05/44.1 kHz with `soxr` and feed 20-ms / 10-ms hops; they then add 64–130 ms of algorithmic delay (BeatNet window + its 84 ms streaming offset; madmom 46 ms frame) that the timestamp arithmetic must subtract.
- One clock, three sources (recommended): state = {tempo_bpm, beat_phase (seconds to next beat), beat_in_bar, bar_number, confidence}. (1) The TRACKER updates tempo and beat_phase every beat (alpha-filter with gain by confidence) and never touches beat_in_bar/bar_number on its own. (2) The TAP sets beat_in_bar = 1, bar_number from the song-part map, tempo (initial) and phase; it stays the authoritative restart gesture. (3) REFERENCE ALIGNMENT — the stored reference recording annotated offline with Beat This! into a bar grid plus the existing part map — supplies the coarse position in bars (e.g. online DTW on chroma/ODF against the reference, evaluated once per bar) and corrects bar_number/beat_in_bar when it disagrees with the running count by a whole bar for ≥2 consecutive bars; the live beat phase from the tracker is what makes the alignment's time resolution unnecessary (alignment can be coarse and slow, the tracker fine and fast). (4) Confidence feeds the UI: LOCKED → clock free of taps; COASTING → clock runs at last tempo, lyrics keep scrolling, cues still fire; UNLOCKED → "tap two bars" prompt, cues suspended or fired on the tap.
- Where downbeat evidence from audio fits: as a third vote (kick/snare bar matcher, or BeatNet+ if ever installed) that can raise or lower the bar-phase confidence and trigger the "are we a bar out?" check, never a silent override — given ≤57% online downbeat F1, silent override would be wrong almost half the time.

### Gaps
- No source quantifies PortAudio/WASAPI timestamp accuracy on Windows or clock drift between an audio interface and `time.perf_counter()`; the running-offset approach is standard practice but its residual error on this laptop/interface is unmeasured.
- No published "online alignment + beat tracker" fusion for live performance was found in this research pass (score-following literature exists but was out of scope); the fusion design above is engineering inference.
- The audio interface model is unknown; whether it supports a second input channel for a room mic, and its driver's latency reporting, are open questions for the developer.
